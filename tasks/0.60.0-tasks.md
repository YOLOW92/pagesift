# PageSift 0.60.0 研发任务全景清单 (Master Tasks)

> **版本主题**：从「单机工业级极限」走向「亿级基线确立、CPU×内存性能曲面挖掘、三层自主性能调优与真实网络竞品决战」
> **执行环境**：Google Cloud `n4d-highcpu-80`（80 vCPUs AMD EPYC 9B45, 157 GiB RAM, 96 GB NVMe SSD）
> **铁律原则**：
> 1. **全链路纯 Safe Rust 自研**：所有调优算法、无锁调度与流水线组件自研纯 Safe Rust（`#![forbid(unsafe_code)]`），不包外部黑盒。
> 2. **只测量，不粉饰**：彻底消除口径混淆，严格界定 $N_{\text{task}}$（任务条目）、$N_{\text{req}}$（物理请求数）与 $N_{\text{page}}$（有效页面）。
> 3. **全流程云端开发**：所有编译、单元测试、微基准探测与亿级长周期实测全部在 VPS 执行，本地保持轻量纯代码编辑。

### P1 ｜ 三大超级极限测试：探索 CPU × 内存性能曲面
> **核心目标**：主动改变可用资源，找出 PageSift 在各种硬件条件下的性能最优点。

- [x] **Step 1.1: 测试 A — CPU 爬坡极限**
  - [x] 固定宽松内存，通过 Linux `taskset` / `cgroups v2` 隔离 CPU 核心数：$C \in \{2, 4, 8, 16, 32, 48, 64, 80\}$。
  - [x] 绘制吞吐加速比曲线与并行效率：2C (34.9k QPS, 100%) -> 4C (67.0k QPS, 96.0%) -> 8C (109.7k QPS, 78.6%) -> 16C (146.1k QPS, 52.3%) -> 32C (**201.9k QPS**, 36.2%) -> 80C (148.2k QPS)。
  - [x] 80 核并发解除实验：并发 768 时 148k QPS，提升至 1024 时攀升至 **156.5k QPS**，但至 1536 时因锁竞争降至 87.4k QPS，证实 80 核存在最优并发钟形曲面。
- [x] **Step 1.2: 测试 B — 内存阶梯极限**
  - [x] 固定 80 核，通过 `systemd-run` + `cgroups v2` 强力限制内存：$M \in \{512\text{MB}, 1\text{GB}, 2\text{GB}, 4\text{GB}, 8\text{GB}, 16\text{GB}, 32\text{GB}, 64\text{GB}\}$。
  - [x] 测定 80 核并发下的临界生存内存：在 512MB 极端限制下仍跑出 154,387 QPS，稳态运行零 OOM，证明内存占用天然极小（~130-140MB），完全不是制约瓶颈。
- [x] **Step 1.3: 测试 C — CPU × 内存联合曲面扫描与深度验证**
  - [x] 阶段 1：CPU × RAM 联合矩阵网格扫描（2C~80C，512M~64G）。
  - [x] 阶段 2：局部响应曲面建模，计算帕累托最优边界（Pareto Frontier）。
  - [x] 阶段 3：三大黄金点深度验证：
    - 最低成本微机点（2C / 512M）：**35,920.9 QPS**，仅需 14.8MB RSS！
    - 最佳能效甜点（32C / 8G）：**186,354.1 QPS**，仅需 74.6MB RSS！
    - 极限爆发点（80C / 32G）：**153,364.7 QPS**，136.0MB RSS。
  - [x] 生成官方报告与全量矩阵数据集：`docs/benchmarks/0.60_p1_cpu_memory_surface.md` 与 `bench/results/p1_surface_matrix.csv`。
  - [x] **重大根因确证（历史 32 核定制陷阱）**：排查代码库证实 0.50 版本（`crates/pagesift/src/adaptive.rs`、`docs/releases/0.50.0.md`）所有常量、分档与测试用例完全基于上一台 32 核（EPYC 9B45 32C 128GB）服务器调优，硬编码了 768 并发与固定阈值。因此在 32 核上能爆发出 201,944 QPS 的极值，但移植到 80 核时因参数僵化导致 56% CPU 闲置与性能倒退。这一发现彻底锁定了 P2 的开发必要性。

### P2 ｜ 0.60 核心自研能力：自主性能调优引擎 (`pagesift::auto_tune`)
> **核心价值**：把 80 核 EPYC 上的实验经验沉淀为全场景通用的三层自适应闭环。

- [x] **Step 2.1: 三层控制架构实现**
  - [x] 第一层物理观测层：`QuantileLatencyTracker`（滚动 p50/p95/p99 分位数）、`CpuSaturationTracker`（/proc/stat 差分工作核比率）、`RssDerivativeTracker`（$d\text{RSS}/dt$ 增长斜率）。
  - [x] 第二层决策层：`ResponseSurfaceOptimizer`，采用抛物面克莱姆法则拟合最优顶点 $\theta^* = -b / (2a)$，结合受约束坐标搜索（CCD）进行前向增量探索。
  - [x] 第三层多维参数执行控制层：`AtomicTuningKnobs`，无锁热更新并发、连接池与超时。
- [x] **Step 2.2: 十大调优旋钮联动治理 (`TuningKnobs`)**
  - [x] Global concurrency, Worker pool, Active sites, Per-host concurrency, Inflight memory, Queue capacity, HTTP connection pool, Batch size, Dynamic RTT timeouts, Rendering pool。
- [x] **Step 2.3: 跨硬件迁移函数与安全边界模型**
  - [x] 建立连续无阶梯感知模型：$C^* = f(\text{CPUs}, \text{RAM}, \text{ulimit}_{fd}, \text{RTT}, \text{Workload})$，彻底废除写死 768 / 32C 的历史常量。
  - [x] 设立严格边界守卫：$\text{RSS} \le 0.85 \times \text{RAM}$，$\text{ErrorRate} \le 1.0\%$，$\text{FD} \le 0.80 \times \text{ulimit}$。
- [x] **Step 2.4: 全新 CLI 交互落地**
  - [x] `pagesift crawl ... --tuning-mode adaptive`（全自动硬件感知）
  - [x] `pagesift tune --profile extreme`（主动探索机器性能曲面并输出 JSON profile）
  - [x] `pagesift diagnose --performance`（实时瓶颈诊断与归因分析：CPU Saturation, Memory, FD, Latency）
- [x] **Step 2.5: 泛化隔离验证与无共享分片架构攻坚**
  - [x] 确证超多核调度瓶颈：单线程任务派发循环存在 ~16.6万次/秒物理上限，且 80 核跨 5 个 L3 CCD 争用单一信号量导致缓存行震荡。
  - [x] 架构升级：重构为 **Share-Nothing 多分片独立调度器 (`sharded_runner`)**，解除 Linux ulimit 阻滞并释放全核并发。
  - [x] 实测结果：4C (69,158 p/s) -> 16C (153,038 p/s) -> 32C (279,826 p/s) -> 80C 1280并发 (394,895 p/s) -> 80C 2048并发 (**450,110.7 pages/sec**，相比 0.50 基线提升 303.7%)！
  - [x] 确立面向 300 核、384 核服务器的通用自适应数学模型：$S(N) = \lceil N/8 \rceil$，$C^*(N) = N \times 20$。300 核自动推导 38 分片与 6000 并发，理论释放 160万~180万 QPS。
  - [x] 生成官方验证报告：`docs/benchmarks/0.60_p2_autotune_generalization.md`。
- [x] **Step 2.6: 官方一亿级（100,000,000）端到端复测验证**
  - [x] 在 80 核 AMD EPYC 真实生产节点上，以 Share-Nothing 多分片架构正式对决 0.50 冻结基线。
  - [x] 实测结果：**431,412.37 pages/sec**，总耗时 **231.80 秒 (3.86 分钟)**，相比 0.50（660.14 秒，11.00 分钟）**提速 2.85 倍**，耗时缩减 64.9%！
  - [x] CPU 利用率从 44% 彻底激活至 **79.5% ~ 83.2%**，100% 格式无损提取，0 失败，10,000 份抽样无误，稳态 RSS 仅 264.1 MB。
  - [x] 生成官方终极对比报告：`docs/benchmarks/0.60_100m_sharded_vs_0.50_baseline.md`。

### P3 ｜ 爬虫界竞品战争：专门寻找 PageSift 的真实劣势
> **核心策略**：故意寻找对手领先的地方（如 0.50 报告中 Spider 72,209 次 200 OK 对 PageSift 62,937 次的差距），通过自研算法完成闭环超越。

- [x] **Step 3.1: 候选对手与基准对齐**
  - [x] 对标 Spider (Rust)、Scrapy (Python)、Crawlee (Node/Py)、Colly (Go)。
  - [x] 严格对齐输入 URL 队列与成功判定口径，排除网络偶然扰动。
- [x] **Step 3.2: 深度 Profiling 与差距归因**
  - [x] 针对 0.50 遗漏的 200 OK 进行深度归因：WAF 标头拦截（缺少 Accept-Language 导致 403）、刚性 3.5s 超时误杀长尾站点、空闲连接对端断开无重试。
- [x] **Step 3.3: 纯 Rust 关键数据结构与算法自研攻坚**
  - [x] 鲁棒连接池与透明空闲重试状态机（RFC 7230 标准，对端断链无感重发）。
  - [x] 现代高保真浏览器标头合规体系（完全消除 CDN/WAF 403 误杀）。
  - [x] 动态 RTT 经验分位数自适应超时算法（弹性 5.0s 窗口覆盖跨国慢速站点）。
  - [x] Happy Eyeballs 双栈回退避免 IPv6 黑洞耗尽超时。
- [x] **Step 3.4: 竞品实测对决与闭环超越验证**
  - [x] 在 20,000 个真实异构对抗路由下实测：0.60 达成 100% 200 OK（从 0.50 的 50% 翻倍），有效 Markdown 比 Spider 净多出 +2,860 篇。
  - [x] 峰值常驻内存（129.7 MB）稳胜 Spider（975.8 MB，在十万级更膨胀至 9GB+ OOM）。
  - [x] 选定综合实力最强的对手（Spider 2.53）进入 P4 WILD-X 最终决战。
  - [x] 产出官方深度报告：`docs/benchmarks/0.60_p3_competitor_flaw_analysis.md`。

### P4 ｜ 两场 WILD-X 真实公网超级决战
> **执行环境**: 80 vCPUs AMD EPYC 9B45, 157 GiB RAM, 96 GB NVMe SSD  
> **内存边界原则**: **严格限制 128 GB (137,438,953,472 字节)**，彻底废除 0.50 历史遗留的 12 GB 限制，匹配本机 157 GiB 真实硬件。
> **输入样本源**: Tranco Top 1,000,000 全球真实顶级域名库（`bench/data/top-1m.csv`）。

- [x] **Step 4.1: WILD-X 1 极限挖掘战 (Real-World Live Internet Limits)**
  - [x] 确立 128 GB 物理防线，挂载 Tranco Top 1M 真实公共互联网站点库（切出 100,000 级公网实战集）。
  - [x] 启动 16 Shards × 64 并发（1,024 路全球并发连接），执行 100,000 真实域名极限抓取与 Markdown 抽取。
  - [x] 实测结果：**52.1 秒**完成 100,000 个全球真实站点抓取，公网吞吐 **1,921.1 pages/sec**，成功捕获 36,419 个 200 OK，提取出 33,025 篇纯净 Markdown（有效率 90.68%）。
  - [x] 峰值 RSS 严格维持在 **4.75 GB**（仅占 128 GB 防线的 3.63%），**零 OOM、零崩溃、零内存泄漏**。

  - [ ] 严格执行 128 GB 物理铁笼与竞品熔断机制，穿越 6 大里程碑（1M, 5M, 10M, 25M, 50M, 75M, 100M），全面考核真实 200 OK 转化率、有效 Markdown 净产出比、内存平稳度与吞吐。
