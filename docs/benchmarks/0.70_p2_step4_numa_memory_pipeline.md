# PageSift 0.70 P2 第四步：NUMA 本地内存与融合解析流水线

> 日期：2026-10-25  
> 环境：Google Cloud `c4-highcpu-192`，Intel Xeon Platinum 8581C，192 vCPU / 96 物理核 / 2 Socket / 4 NUMA  
> 判定：第四步通过。内容纯 CPU 中位吞吐提升 `10.29%`，完整 Reactor 链路维持零失败并小幅增效，峰值 RSS `244.72 MiB`，低于 `500 MiB` 门槛。

## 实现

### Worker 本地容量复用

- `pagesift_html::ParseScratch` 复用 DOM 节点、属性和实体解码缓冲；
- `pagesift_content::ProcessWorkspace` 复用正文判定所需的 visible、block、cache、class、feature、attachment 和遍历顺序数组；
- 新增 `process_with_workspace`，输出 Markdown/metadata 仍为独立所有权，DOM 和索引容量在页面结束后归还原 Worker；
- 生产 `spawn_blocking` 路径使用 thread-local `ProcessWorkspace`，避免 DOM 容量在不同阻塞线程/allocator arena 间分配释放；
- 自研 Reactor 每个固定 Reactor 线程拥有一个 workspace，保持 NUMA first-touch 所有权；
- 超过 16,384 节点或 32,768 属性的大页不永久滞留在 workspace，避免少数异常页面放大 192 Worker 常驻内存。

默认路径每页至少重新建立 9 个主要 backing vectors（DOM nodes/attrs，加 7 个正文索引数组），实体解码缓冲按需分配。workspace 路径在暖机后只在页面超过既有容量时增长；Markdown、metadata 和调用方要求的可选输出仍按页独立分配，不以缓存破坏返回值所有权。

### Reactor/解析融合

- Content-Length 和 close-delimited 正文直接借用连接接收缓冲，不再先复制到临时 `Vec<u8>`；
- chunked 响应仍经过自研解码缓冲，保持 framing 正确性；
- 固定 fixture 的最终 URL 预解析并缓存；请求页号直接编码到复用字节缓冲，不再每页 `format!`；
- Linux `epoll`/Mio 的 `EINTR` 作为可恢复中断继续轮询。测试中曾在 99.52% 触发一次；失败轮已排除且修复后候选全部完成。

## 内容纯 CPU A/B

共同条件：相同 5 种页面、10,000,000 次处理、192 Worker，CPU 仅统计 Runner `/proc/self/stat` 的 `utime + stime`。

| 路径 | 三轮 pages/s | 中位数 | 峰值 RSS 范围 | failed |
|---|---|---:|---:|---:|
| 每页新建 DOM/索引容量 | 1,835,254 / 1,762,263 / 1,049,215 | 1,762,263 | 161.31–161.39 MiB | 0 / 0 / 0 |
| Worker `ProcessWorkspace` | 1,913,458 / 1,943,666 / 2,005,449 | **1,943,666** | 160.90–161.34 MiB | 0 / 0 / 0 |

中位吞吐提升 `10.29%`。旧路径第三轮存在明显调度低谷，因此同时保留全部原始轮次，不用单次峰值作结论。workspace 三轮跨度 `4.81%`。

## 完整 Reactor 验证

共同条件：12 路 `SO_REUSEPORT` 本机源站、1,536 连接、192 Reactor、5 个固定页面、每轮 10,000,000 页。

| 路径 | 三轮 pages/s | 中位数 | Runner CPU 中位 | 单核产出中位 | failed |
|---|---|---:|---:|---:|---:|
| 第三步 Reactor | 913,012 / 920,359 / 902,892 | 913,012 | 134.31 核 | 6,804 pages/core-s | 0 |
| 第四步融合路径 | 938,237 / 908,475 / 916,514 | **916,514** | **131.99 核** | **6,919 pages/core-s** | 0 |

端到端中位吞吐提升 `0.38%`，Runner CPU 时间中位从 `1,469.62` 降至 `1,445.32 core-s`（`-1.65%`），单位 CPU 产出提升 `1.68%`。内容阶段已有两位数提升，但完整链路再次受到源站/Reactor 节奏约束，所以不夸大整体增幅。

独立 RSS 验证为：`927,273.46 pages/s`、`failed=0`、`peak_rss_bytes=256,606,208`（`244.72 MiB`），低于第四步 `500 MiB` 安全线。
