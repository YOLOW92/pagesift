# 0.70 十域对决 · D1 正文提取（本机同机重测）

**目的**：0.50 那张十域表的 D1 用的是 0.40 时代的数字（3,525 p/s），且硬件与本次不同。
这里在本机同机重跑 0.50 与 0.70，并用同一套指标与竞品对比。

## 口径

| 项 | 值 |
| :--- | :--- |
| 机器 | Intel i7-10700，8 物理核 / 16 逻辑核，15 GB 内存，Ubuntu 26.04 |
| 数据 | WCXB 官方 2,008 页 → 有参考正文的 **2,006 页**（7 类页面） |
| 指标 | word-level F1（`bench/fresh/wcxb.py` 的 `plain()` + `word_f1()`，与 0.50 报告同一函数） |
| 内存 | 每个参赛者 **10 GiB 上限**（cgroup `memory.peak` 取峰值），超限即 OOM 记失败 |
| 并发 | 统一 **16 分片并行**，`--cpuset-cpus=0-15`，不人为限核 |
| 容器 | 全部在容器内跑，`--network=host`，同一挂载与同一输入清单 |

## ⚠️ 关键发现：0.70 在 WCXB 上劣于 0.50

| 页面类型 | 0.50 F1 | 0.70 F1 | Δ |
| :--- | ---: | ---: | ---: |
| article | 0.7220 | 0.7212 | −0.0007 |
| documentation | 0.7421 | 0.7294 | −0.0127 |
| product | 0.5580 | 0.5254 | −0.0326 |
| forum | 0.6615 | 0.6279 | −0.0336 |
| collection | 0.5668 | 0.5299 | −0.0368 |
| service | 0.6722 | 0.6351 | −0.0371 |
| listing | 0.6234 | 0.5652 | −0.0582 |
| **总计** | **0.6824** | **0.6652** | **−0.0173** |

精确率 **+0.0409**、召回率 **−0.0506**。

归因：0.70 把「正文定位」从仅 `og:type=article` 放开到**所有页面**。
文章页本来就走文章模式，所以几乎不变（−0.0007）；而论坛、列表、商品、聚合、服务页
的参考正文是**整块的页面内容**，被当成"正文容器"裁掉后召回明显下降。

这解释了为什么 WebMainBench 上升、WCXB 下降：两个基准对"主内容"的定义不同。
WebMainBench 的参考是 `convert_main_content`（偏文章主体），收窄有益；
WCXB 的非文章类参考是整页内容，收窄有害。

## 结论与建议

1. **不能对外宣称 0.70 的抽取质量全面优于 0.50**。目前是"某一类基准上升、另一类下降"。
2. 这个默认值（`PAGESIFT_NO_FORCE_ARTICLE` 未设时全页尝试正文定位）建议改为：
   - 要么**默认关闭**，把 WebMainBench 的收益变成可选；
   - 要么**按页面结构判断**：能识别出文章型结构才收窄，论坛/列表/商品页保持整页输出。
3. 速度上 0.70 与 0.50 基本持平（2,408 vs 2,565 页/秒，−6%），
   与 200M 合成页测出的 −13% 不同，原因是本域按 16 进程分片跑，分片开销与页型混合稀释了差异。
