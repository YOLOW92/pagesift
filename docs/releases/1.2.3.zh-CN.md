# PageSift 1.2.3 更新日志

> **版本：**`v1.2.3` · **日期：**2026-11-09 · **许可：**AGPL-3.0-only，另提供商业许可

相对于 1.2.2 的变更。另有 [English](1.2.3.md)、[日本語](1.2.3.ja.md)、[Español](1.2.3.es.md)。

## 图片资产

- `imageAssets` 为可选项：scrape、batch 请求直接设置，crawl 放在 `scrapeOptions`。不设置时保持原来的纯链接行为。`attach` 保留 Markdown 链接并在附件中返回 Base64 字节；`embed` 写入 data URL；`rewrite` 改写为 `asset://<id>` 并返回附件。CLI 的 scrape、crawl 支持 `--image-assets attach|embed|rewrite`。
- 资产 ID 来自导出字节的 SHA-256，并提供完整哈希、按内容识别的 MIME、字节数和来源。`imageAssets` 逐图记录 `ok`、`skipped-limit` 或 `failed`，后两者提供原因；不只相信扩展名或 HTTP Content-Type。
- 同一 batch/crawl 中，`attach`、`rewrite` 对相同内容只在首次发布时携带 Base64，后续页面引用同一 ID。持久化任务的字节保存在内容寻址附件库，读取首次发布页时重建 Base64；分页客户端应保留前页资产，或在资源仍可用时通过附件接口读取。`embed` 每页独立离线可用，因此跨页允许重复 data URL。
- 网页图片遵守现有 robots、限速、重定向和 SSRF 策略；每页有字节预算，最多请求 64 张、总耗时上限 10 秒、最多并发 4 张。失败或超限的图片保留原链接。任务内缓存最多 32 个 URL、单图最多 512 KiB，持久化任务重启时从成功记录恢复；大图、超出缓存的 URL、不同 URL 的相同内容仍可能重复下载。
- SVG 只允许作为附件或 `asset://` 引用，**不会**由新增 `embed` 模式写入 data URL；格式识别不等于消毒。源页面原有 data URL 由 `removeBase64Images` 单独控制。
- PDF XObject 图片可独立于 OCR 输出；转为 PNG/TIFF 时按实际导出字节计算 ID，并同步 Markdown 引用。PDF inline image 不在本管道中。DOCX、PPTX、XLSX 的 ZIP 媒体保留原始字节；邮件图片附件未接入本管道。
- HTTP scrape/batch/crawl 返回资产；CLI `--out` 将图片写入 `images/<id>`，并在 `index.jsonl` 记录结果。MCP scrape 使用原生 image content；`embed` 的自包含 Markdown 保留在文本块，含 data URL 的对应结构化 Markdown 会省略以减少一份重复，文本和原生图片块仍各含一份字节。

## 流式输出和兼容性

- `POST /v2/scrape/stream` 可在图片下载结束前发送正文初稿，再发送完整结果；batch/crawl 流增加可选 `?previews=true` 初稿事件。初稿最多 1 MiB，可能丢弃、不持久化也不重放；正式页面的序号和续传语义不变。普通 JSON 仍在资产处理完成后返回。
- `removeBase64Images: false` 现在被接受，保留源页面中的 data URL 图片；默认 `true` 继续剥离。两个选项使用不同缓存键。
- 原有 `exportImages` 保留。新模式的首份附件 JSON 包含 MIME、Base64 `data` 和 `inlineData` 标记；接口和限制详见[图片资产说明](../image-assets.md)。

## 自研 Base64 与三方对比

- 新增 `pagesift-base64`，支持标准和 URL 安全字母表、可选填充、严格和空白宽容解码、流式解码及单次分配 data URL。AVX2、NEON 运行时检测，不支持时走标量路径。CDP、MCP、代理认证及图片资产管道使用新 crate；Office MIME 继续使用原有更宽容的解码器。
- 同进程对比自研、`base64` 0.23.1、`base64-simd` 0.8.0，机器为 Intel i7-10700。1 MiB 严格输入的编码时间依次为 **57.8714 / 422.6966 / 102.6861 微秒**，解码为 **55.0611 / 502.2591 / 135.9397 微秒**；越低越好。8 字节严格编码依次为 **0.0110 / 0.0090 / 0.0073 微秒**，并非所有尺寸都领先。
- [完整对比表](1.2.3-benchmarks.md)列出 13 个尺寸的严格编码、严格解码和 CRLF 宽容解码，以及测试条件、短输入差距和各库宽容语义差异。结果为单机热缓冲微基准，并非端到端网页抓取速度。
- AVX2 实现参考 MoeForge/moego 的技术，许可与出处见 [`THIRD-PARTY.md`](../../crates/pagesift-base64/THIRD-PARTY.md)。ARM NEON 已交叉编译检查；该性能对比没有在 ARM 实机运行。
