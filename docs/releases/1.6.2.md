# PageSift 1.6.2 Release Notes

> **Release Version**: `v1.6.2`  
> **Release Scope**: Upgrade compatibility for persisted `1.6.0` tenants, async quota-settlement cancellation safety, Rust `KeyLimits` builder ergonomics, and monitor `/run` concurrency serialization on the `1.6.x` line (`v1.6.1 -> v1.6.2`)

PageSift `1.6.2` resolves upgrade continuity, quota-settlement cancellation safety, Rust source-compatibility documentation, and monitor scheduling concurrency edge cases surfaced right after `1.6.1`.

## Highlights

- **Seamless `1.6.0` Persisted Tenant Upgrade Continuity (`pagesift-store`, `pagesift-cluster`, `pagesift-api`, `pagesift-engine`, `pagesift`)**:
  - Adds `Store::existing_tenants`, `Ledger::has_account_usage`, `Engine::store`, and startup key resolution (`account_resolve::resolve_callers`) so upgrading an existing `1.6.0` deployment preserves access to persisted `Context`, `DataGraph`, `Loop` sources, `Monitors`, `Jobs`, and daily page quotas without manual data migration.
  - Unnamed keys (`api_keys`) with existing `1.6.0` FNV-1a (`key-<16hex>`) persisted data and uniquely-named keys (`[[server.keys]].name`) with existing data under that name retain their legacy namespace automatically (with a startup log advising operators to pin explicit `account = "<name>"` for named keys).
  - Multiple keys sharing the same display `name` without explicit `account` remain strictly isolated under SHA-256 fingerprints (`key-<32hex>`) and emit an actionable startup warning if legacy data exists under the shared display name. Fresh keys with no legacy store data use SHA-256 fingerprints directly.
- **Cancellation-Safe `PageHold::commit()` Quota Settlement (`pagesift-api`)**:
  - Transitions in-memory `held -> settled` synchronously inside `PageHold::commit()` before any `.await` point, eliminating the cancellation window where dropping `commit()` while waiting on a per-account write lock could leave `held` quota permanently occupied until UTC midnight.
  - Runs per-account serialized quota persistence inside a detached `tokio::spawn` task awaited by `commit()`, ensuring write locks are never dropped mid-write and settled usage flushes reliably to `Store` even if the HTTP caller cancels mid-commit.
- **Rust `KeyLimits` Ergonomics & Explicit Compatibility Boundary (`pagesift-api`)**:
  - Preserves `KeyLimits.account: Option<String>` (introduced in `1.6.1`) and adds forward-compatible fluent builders (`KeyLimits::new()`, `.with_name()`, `.with_account()`, `.with_requests_per_minute()`, `.with_max_concurrent_jobs()`, `.with_pages_per_day()`).
  - HTTP/CLI/MCP/Python/Node.js/C ABI wire formats remain backward compatible across `1.6.x`; Rust callers constructing `pagesift_api::KeyLimits` or `pagesift::config::ApiKey` via exhaustive struct literals (without `..Default::default()`) should include `account: None` or use `..Default::default()` / `KeyLimits::new().with_*()`.
- **Per-Monitor Execution Serialization (`pagesift-api`)**:
  - Serializes background scheduled checks (`run_check`) and manual `POST /v2/monitor/{id}/run` calls per monitor ID (`Monitors::run_locks`, `run_check_locked`) and skips emitting empty `pages: []` checks when a concurrent run already advanced `next_due`, fixing the race condition observed in `monitor::tests::checks_spend_the_page_quota` on macOS CI.
