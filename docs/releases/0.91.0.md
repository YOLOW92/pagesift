# PageSift 0.91.0 Release Notes: Failures That Are Reported

> **Release Version**: `v0.91.0`
> **Release Date**: 2026-11-03
> **License**: AGPL-3.0-only (Commercial licensing available)

---

## Overview

0.91 fixes the problems found in a code review of 0.90.0 (commit `1ef27b1`). Most of them are failure paths
that 0.90 logged and then reported as success: a job page that could not be saved, a job record that could not
be replicated to the standby, a webhook event that was never delivered. 0.91 reports them. It also fixes two
content problems (small JSON-LD islands, an unbounded block merge) and narrows what 0.90 claimed about warm
standby, the quality score and the Jina SSE stream.

Every fix below is covered by local tests only (no real websites are involved). The tests, and for each one
whether it fails on 0.90.0 or tests an interface 0.90.0 does not have, are listed in
[`docs/history/0.91_review_fixes.md`](../history/0.91_review_fixes.md).

**Behaviour changes to know about when upgrading:**

- A crawl or batch job whose results cannot be saved (store write error, or replication to the standby failing)
  now stops and ends as `failed`, with the reason in `GET /v2/crawl/{id}/errors`. 0.90 kept going and ended
  as `completed`, and the unsaved pages were missing after a restart.
- Job-level errors (quota reached, the reason a job failed) are stored in their own list and no longer count
  as completed pages after a restart.
- Webhook events that were never delivered (retries used up, or target blocked) appear in the job's errors with
  code `WEBHOOK_FAILED` and their `eventId` (jobs with a store only).
- Cluster: only the worker id configured as `[cluster] standby` can receive the gateway's journal; workers can
  no longer submit or cancel tasks over the cluster protocol, or commit or renew a lease held by another
  worker. A gateway with `journal = true` but no `standby` id now refuses the standby's connection.
- A standby that failed to apply a replicated job record refuses to take over.
- **A gateway with a configured `[cluster] standby` now uses lease fencing (default):** it accepts writes only
  while the standby keeps acknowledging the journal, so it refuses writes after a restart until the standby
  has acknowledged, and it stops writing when the standby stops (crash or network split). `[cluster] fencing =
  false` restores the 0.90 behaviour. The cluster protocol is now version 2; version 1 peers still connect,
  without fencing.
- An `engine: browser` request on a machine where a browser was found but cannot start (for example when
  running as root) returns `UPSTREAM_ERROR`, as when the browser exits at launch; it returned
  `UNSUPPORTED_OPTION` in 0.90. No browser found at all is still `UNSUPPORTED_OPTION`.
- New `[fetch] env_proxy` (default `true`): set it to `false` to ignore `HTTPS_PROXY` / `HTTP_PROXY` /
  `ALL_PROXY` from the environment.
- Path families with learned render decisions can render more often than in 0.90 (see *Render decisions*);
  they still never render where the 0.81 rule would not.

## Job results

- **Store write failures:** a page or page error that cannot be saved is not counted as completed and does
  not send a `page` webhook event; the job stops and ends as `failed`. A failure to save the crawl queue (used to
  resume after a restart) does the same.
- **Replication failures (gateway):** `JobLog::append` returns an error. When the local write succeeded but the
  record could not be handed to the ledger journal, the page counts as completed (it is in the local store), and
  the job stops and fails because the standby no longer has the same records. After the first failed record of
  a write, the later records of that write are not sent either, so the standby's lists do not shift.
- **Errors that cannot be stored either** (the disk is full) stay in memory, so `GET /v2/crawl/{id}/errors`
  shows the reason while the process runs; after a restart the job resumes from what was stored. Tested by
  making every store write fail mid-crawl (`Store::fail_writes`, a fault-injection hook).
- **Standby replay failures:** a replicated job record that the standby cannot apply is counted
  (`Ledger::app_failures`); such a standby refuses to take over until it is resynchronised from an empty data
  directory.
- **Job-level errors** are replicated to the standby (0.90 wrote them only to the local store).

## Webhooks

An event now ends in one of four states, documented in `crates/pagesift-api/src/webhook/queue.rs`: queued on
disk, delivered, not delivered (dead letter, in the job's errors as `WEBHOOK_FAILED`), or moved to the memory
queue after a store error. The move to the memory queue is counted in `/metrics` as
`pagesift_webhook_deliveries_total{outcome="degraded"}`; events in the memory queue are lost if the process
crashes. Without a store, undelivered events are only counted (`outcome="failed"` or `"blocked"`) and logged,
as in 0.90.

## Attachments

With a store (job persistence on), `exportImages` attachments are also written to the store and
`GET /v2/attachments/{id}` reads them from there when they are no longer in memory (restart, or evicted by
newer images). They expire with the job results (24 h); expired entries are deleted at start-up and on access.
On a gateway with a standby, attachments are replicated with the job records and included in snapshots; one
attachment larger than half the cluster frame limit is stored locally only (logged). Without a store they stay
in memory only, as in 0.90.

## Content

- **Page data islands with few strings:** with fewer than ⌈1/δ⌉ = 20 string values, the `q(1−δ)` cut-off is the
  longest string itself, so 0.90 extracted nothing from a typical `application/ld+json` article (`@type`,
  `headline`, `articleBody`, …). With fewer than 20 strings the cut-off is now the largest gap in the sorted
  string lengths. Tests cover 1, 2, 3, 5, 10, 19 and 20 strings, equal lengths, no prose, a long body, several
  islands and HTML strings. A 0.90 test of this path returned early when no candidate came back; it now has to
  produce one.
- **Block merge cost:** the alignment of two candidates' unmatched blocks is limited to as many matrix cells as
  the two candidates have bytes of text. A region over the limit takes the blocks of the candidate with the higher
  quality score instead of matching them one by one. Two candidates with 5,000 unanchored blocks each (the
  test): 0.90 took 9.4 s in total for two merges and peaked at 598 MB resident; 0.91 takes 0.03 s (quick
  profile, the 4-CPU development VM of this release, `merge::tests::huge_unanchored_gap_stays_linear_and_keeps_the_better_side`).

## Render decisions

The quality score was fitted to the label "recall not in the lowest δ of its benchmark set"
(`docs/history/0.83_quality_calibration.md`: positive rate 0.951; Firecrawl's cut-off recall is 0.004). It
ranks two results of the same page; it is not the probability that a result is complete. 0.90 used `1 − Q_http`
as the value of rendering: with a 1 s render and 30 s left, `p·(1 − 0.97)` cannot exceed the charge 1/30 for
any `p`, so a family whose renders always helped stopped rendering once its HTTP results scored 0.97. A learned family now renders when `p > E[render seconds]·(λ_browser +
1/remaining deadline)`, `p` being the sampled probability that rendering helped in that family. The decision
is still taken only inside the 0.81 candidate gate. `explain` reports `value` = 1 for these steps.

Measured on this release's machine (WebMainBench 545 pages from a local site, `engine: auto` with `explain`,
Chromium 1243 run as an unprivileged user; `benchmarks/history/0.91/render_wmb.sh`, results
`benchmarks/history/0.91/results/render-20261103`): 9 pages pass the 0.81 candidate gate. 0.90.0 rendered 4 of
them, 0.91.0 rendered 5 (2 by a learned decision, 0 in 0.90.0); mean recall against the reference text 0.9217
for both (higher is better). Nine gated pages are too few to say more than that the direction is as expected.

How far the score is from an absolute probability, same 545 pages, built-in model, label "recall ≥ τ"
(`examples/quality_eval.rs`, `results/quality-absolute-wmb.json`; WebMainBench was one of the four 0.83 fitting
sets, so this is in-sample):

| Label | mean prediction by score quartile | observed share by quartile | Brier model / constant (lower is better) |
|---|---|---|---|
| recall ≥ 0.5 | 0.894, 0.978, 0.988, 0.991 | 0.846, 0.971, 1.000, 1.000 | 0.028 / 0.044 |
| recall ≥ 0.8 | same | 0.750, 0.897, 0.941, 0.956 | 0.089 / 0.101 |
| recall ≥ 0.9 | same | 0.721, 0.816, 0.853, 0.912 | 0.146 / 0.144 |

The observed share rises with the score, so it ranks results; for "recall ≥ 0.9" it predicts about 0.98 where
0.82–0.91 is observed and is no better than a constant. 0.91 uses the score only to compare results, so it was
not refitted; refitting with an absolute label needs all four 0.83 sets, three of which are not on this machine.

## Jina reader SSE

While a page is fetched or rendered, the stream now sends a `: keepalive` comment every 30 s (the interval of the
crawl and batch streams); SSE clients ignore comments, and the events are byte-identical to 0.90's. The
`content` events still come after the whole page has been extracted: main-content extraction scores the whole
DOM before it knows which blocks are content, so blocks cannot be emitted while the page is parsed.

## CPU workers

Queued plus running CPU tasks are limited to twice the number of workers. `Pool::run` waits for a slot
(first come, first served; a cancelled waiter takes no slot). `Pool::spawn` (decompression handed off by the
network layer) runs the job on the calling thread when no slot is free, as it already does when handing off is
not worth it. 0.90's queues had no limit.

## Multiple servers

- **Lease fencing:** the standby acknowledges every journal batch (heartbeats included) with the window in which
  it promises not to take over. The primary extends its lease to the batch's send time plus that window, on its
  own clock, and refuses every write once the lease has lapsed. The standby declares the primary lost no earlier
  than its last promise plus one heartbeat interval. A batch reaches the standby only after the primary sent it,
  so when the standby takes over the primary's lease has already lapsed and the two never accept writes at the
  same time; the clocks need not agree, only run at rates within one heartbeat interval's share of each other.
  Tested with the primary still serving after its link to the standby fails
  (`tests/faults.rs` `partition_fences_the_old_primary_before_the_standby_takes_over`) and end to end with a real
  crawl (`crates/pagesift/tests/it/cluster.rs` `standby_takes_over_a_running_crawl`).
- **Cost:** with fencing on, the primary also stops writing when only the standby is down. `fencing = false`
  keeps it writing, and then a split between primary and standby can give two gateways that both accept writes.
- **Manual takeover:** `[cluster] takeover = "manual"` makes the standby report the loss and keep reconnecting
  without taking over; restart it with `--role gateway` and `journal = true` on the same data directory.
- **Journal shipping during snapshots (also in 0.90):** reading the journal while a snapshot trimmed it could
  send one record under a run of indices (the records in between were lost on the standby) or start from a
  record that was not a snapshot start (the standby stopped with a journal gap). Reads now use exact indices and
  never start below the trim target, and replay skips records left in front of a snapshot by an interrupted trim.
  `tests/snapshot.rs` `standby_follows_snapshots_and_resyncs` failed 13 of 90 runs under parallel load on 0.90.0;
  0 of 90 on 0.91.0.
- **Worker permissions:** see *Behaviour changes* above. `GatewayConfig` has two new fields, `standby` and
  `submitters` (ids allowed to submit and cancel tasks over the protocol; none by default).

## Speed and output on this release's machine

Measured on the 4-CPU cloud VM used for this release (Intel Xeon 2.10 GHz, 15 GiB, Linux 6.18), `release-fast`
builds of 0.90.0 (`1ef27b1`) and 0.91.0, against a local site serving the 545 pages of WebMainBench
(`WebMainBench_545.jsonl`, opendatalab/WebMainBench commit `5da0972`), `engine: http`. These numbers are
synthetic (no network) and are not comparable with the 0.90.0 release notes, which were measured on another
machine with another page set.

|---|---:|---:|
| Single request, p50 ms (lower is better) | 5.10 (4.88–5.29) | 5.19 (4.99–5.70) |
| Single request, p95 ms (lower is better) | 18.16 (17.35–19.42) | 18.13 (17.77–19.85) |
| 16 concurrent requests, pages/s (higher is better) | 274.0 (269.7–286.9) | 275.4 (259.3–282.9) |

Script `benchmarks/history/0.91/speed_wmb.sh`, results `benchmarks/history/0.91/results/speed-20261103-072644`.

Output: 657 responses (every page with all formats, plus `includeTags` and `engine: auto` on every tenth page,
the 0.84 `snapshot.py` requests) are byte-identical between 0.90.0 and 0.91.0
(`benchmarks/history/0.91/compare_wmb.sh`, `results/compare-20261103-072825`). The data-island change did not
apply to any of these pages. The block-merge limit and the render-decision change only act when a browser
result exists; see *Render decisions* for the run with a browser.

## Corrections to the 0.90.0 release notes

- "Jina reader SSE: frames are written as soon as they exist." The stream opens at once, but `progress`,
  `content` and `done` are written only after the whole page has been fetched and extracted. The first `content`
  event comes when extraction has finished; it is not incremental extraction.
- "Warm standby … takes over with a higher term." Without fencing (0.90) that was not safe when the primary was
  still running; see *Multiple servers*.
- 0.90.0 described quality comparisons where the one-sided upper bound of new − old was ≥ 0 as "not lower". That
  only means no significant drop was found; it does not bound how large a drop could be. For the 0.88 content
  run (`benchmarks/history/0.88/content/results/paired-20261103.md`) the lowest 95% interval bound over all
  sets and halves is −0.0001, so those results also show non-inferiority for any margin ε ≥ 0.0001. From 0.91,
  `docs/releasing.md` requires a margin ε fixed before the run and a lower bound > −ε.
- 0.90.0 has no cluster throughput measurement (`docs/history/0.89_cluster.md` says so); neither has 0.91.0.
- The single internal data model (`Source`, `Artifact`, `Flow::submit`) and per-output delivery receipts were
  design goals that 0.90 implemented only in part: standalone serving still calls `Scraper` directly, map,
  search, extract and parse run on the gateway, and the CLI outputs write synchronously from
  `pagesift_api::types::Document`. 0.91 does not change this; it is an internal structure, not a behaviour that
  0.90 promised to users.
