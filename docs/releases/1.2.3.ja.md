## 画像アセット

- `imageAssets` は任意指定です。scrape/batch では直接、crawl では `scrapeOptions` に指定し、省略時は従来どおりリンクのみを返します。`attach` は Markdown のリンクを維持して Base64 添付、`embed` は data URL、`rewrite` は `asset://<id>` と添付を返します。CLI の scrape/crawl でも `--image-assets attach|embed|rewrite` を使えます。
- ID は出力バイト列の SHA-256 に基づき、完全なハッシュ、内容から判定した MIME、バイト数、取得元を返します。画像ごとの `imageAssets` 結果は `ok`、`skipped-limit`、`failed` と理由を含みます。拡張子や HTTP Content-Type だけでは判定しません。
- batch/crawl の `attach` と `rewrite` では同一内容の Base64 を最初のページだけに載せ、後続ページは同じ ID を参照します。永続ジョブではバイト列を内容アドレス付き添付ストアに保存し、最初のページの読み出し時に Base64 を再生成します。ページネーション利用時は先のページのアセットを保持するか、利用可能な間に添付 API を使ってください。`embed` は各ページをオフライン完結にするため、ページ間で data URL が重複します。
- Web 画像にも robots、レート制限、リダイレクト、SSRF 対策を適用します。ページごとのバイト予算、最大 64 リクエスト、画像取得全体で 10 秒、最大 4 並列です。失敗・制限時は元リンクを残します。タスク内キャッシュは最大 32 URL、画像ごとに 512 KiB までで、永続ジョブの再開時は成功済み記録から復元します。大きい画像、キャッシュ枠外の URL、異なる URL の同一画像は再取得される場合があります。
- SVG は添付または `asset://` のみで、新規 `embed` data URL にはしません。SVG の形式判定は無害化ではありません。元ページの data URL は `removeBase64Images` で別途制御します。
- PDF の XObject 画像は OCR と独立して出力できます。PNG/TIFF に変換された場合も実際の出力バイト列から ID を計算し、Markdown 参照を更新します。PDF inline image は対象外です。DOCX/PPTX/XLSX の ZIP メディアは元のバイト列を保持し、メール画像添付はこのパイプラインの対象外です。
- HTTP scrape/batch/crawl がアセットを返します。CLI `--out` は `images/<id>` と結果付き `index.jsonl` を出力します。MCP scrape はネイティブ image content を返します。`embed` の data URL 付き Markdown はテキストに残し、重複を減らすため対応する structured content の Markdown は省略します。テキストと image content の間にはバイト列が重複します。

## ストリーミングと互換性

- `POST /v2/scrape/stream` は画像取得完了前に抽出 Markdown のプレビューを送り、その後に最終結果を送ります。batch/crawl のストリームでも `?previews=true` を指定できます。プレビューは最大 1 MiB、ドロップされる場合があり、永続化・再送されません。正式ページのシーケンス ID と再開方式は変わりません。通常の JSON は画像処理後に返ります。
- `removeBase64Images: false` を受け付け、元ページの data URL 画像を保持します。既定値 `true` は従来どおり除去し、キャッシュキーも分離されます。
- 既存の `exportImages` は引き続き利用できます。新モードの初回添付 JSON は MIME、Base64 `data`、`inlineData` を含みます。詳細は[画像アセットガイド](../image-assets.md)を参照してください。

## 独自 Base64 と三者比較

- 新しい `pagesift-base64` は標準/URL セーフ文字、任意パディング、厳密/空白許容デコード、ストリーミング、単一確保の data URL をサポートします。AVX2/NEON は実行時検出し、それ以外はスカラーパスを使います。CDP、MCP、プロキシ認証、画像アセットに適用し、Office MIME は従来のより寛容なデコーダーを維持します。
- Intel i7-10700 上で PageSift、`base64` 0.23.1、`base64-simd` 0.8.0 を同一プロセスで比較しました。1 MiB の厳密エンコードは順に **57.8714 / 422.6966 / 102.6861 µs**、デコードは **55.0611 / 502.2591 / 135.9397 µs** です（低いほど良い）。8 バイトの厳密エンコードは **0.0110 / 0.0090 / 0.0073 µs** で、すべてのサイズで最速ではありません。
- [全比較表](1.2.3-benchmarks.md)には 13 サイズの厳密エンコード、厳密デコード、CRLF 許容デコード、測定条件、小入力での差、許容仕様の違いを記載しています。単一マシンのウォームバッファによるマイクロベンチマークであり、Web 抽出全体の速度ではありません。
- AVX2 の手法は MoeForge/moego を参考にしており、出典とライセンスは [`THIRD-PARTY.md`](../../crates/pagesift-base64/THIRD-PARTY.md) に記載しています。ARM NEON はクロスコンパイルで確認しましたが、この性能比較は ARM 実機では行っていません。
