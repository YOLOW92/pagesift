# PageSift 0.70.0 Release Notes: The NUMA Data-Plane Rewrite

> **Release Version**: `v0.70.0`
> **License**: AGPL-3.0-only (Commercial licensing available)
> **Core Architecture**: Pure Safe Rust (`#![forbid(unsafe_code)]`), hand-written NUMA-local HTTP/1.1 data plane, adaptive closed-loop capacity control

---

## 🌟 Executive Overview

0.60 proved PageSift could finish 100,000,000 tasks. 0.70 replaces the engine underneath that result:
the generic async-HTTP stack is gone, replaced by a **purpose-built, NUMA-local Rust data plane**,
and the whole system is now governed by one closed-loop controller that senses hardware, memory
cgroups and per-origin behaviour instead of trusting fixed constants.

Three outcomes define this release:

1. **Scaling is now measured, not assumed** — 1 → 192 vCPU in one ladder, fitted with the Universal
   Scalability Law.
2. **Memory became a first-class input** — the engine reads its cgroup limit and sizes itself to it.
3. **Extraction quality is reported against public benchmarks** — seven independent suites, published
   number-by-number, including the ones we do not win.

---

## 🚀 Key Highlights

### 1. ⚙️ Hand-Written NUMA-Local HTTP Data Plane

The 0.60 data path funnelled every request through a general-purpose client. 0.70 builds the path
from the socket up, in five layers:

| Layer | What it does |
| :--- | :--- |
| **NUMA-local fixed-slot executor** | Content workers are pinned; each slot owns its buffers for the life of the process |
| **NUMA-local HTTP/1.1 reactor** | Minimal request/response state machine, zero per-request allocation for headers |
| **Hybrid reactor scheduling** | Reactor and content threads share one pipeline; work budget moves between them at runtime |
| **Adaptive per-host connections** | Connection watermarks are per-origin, measured, and closed-loop — a slow host no longer drags the rest |
| **NUMA-native dispatch + work stealing** | Sharded intake with bounded stealing; empty polls are cheap, starvation is visible in telemetry |

Fused parse pipeline: bytes land in the NUMA node that owns the connection, are parsed there, and the
Markdown is produced without a cross-node copy.

### 2. 📈 Scaling Measured 1 → 192 vCPU, Fitted with USL

One ladder, same binary, same fixtures, from a single core to the full 192 vCPU dual-Xeon box:

```
QPS(N) = γ·N / (1 + σ·(N−1) + κ·N·(N−1))
```

| Parameter | Value | Reading |
| :--- | ---: | :--- |
| γ (per-core ceiling) | **8,631.8 pages/s** | single-core ceiling |
| σ (contention) | **1.3407 %** | near-linear; little serialisation |
| κ (coherency) | **0.0000 %** | **no measurable cross-core penalty** |
| R² | 0.8388 | fit quality across the ladder |

κ = 0 is the headline: the data plane does not pay a coherency tax as cores are added, because
nothing is shared on the hot path.

### 3. 🧠 Memory Becomes an Input, Not an Assumption

`HardwareTopology::read_memory()` now reads cgroup v2 `memory.max` and pushes the cap into the
capacity controller. Measured under hard limits:

| cgroup limit | Concurrency | Result |
| :--- | :--- | :--- |
| **768 MiB** | 380 | 50M/50M, 0 failures, **817,346 p/s**, RSS 730 MiB |
| 1 GiB | 1,536 | 50M/50M, 0 failures, 1,063,283 p/s |
| 2 GiB | 1,536 | 50M/50M, 0 failures, 1,068,726 p/s |

At 768 MiB the controller voluntarily shrinks to 380 connections instead of collapsing to the
minimum — memory pressure turns into lower concurrency, not into OOM.

### 4. 🏁 200M Saturation on 192 vCPU

| Metric | Value |
| :--- | ---: |
| Tasks | **200,000,000 / 200,000,000** |
| Failures | **0** |
| Sustained throughput | **947,611 pages/s** |
| Wall clock | **211.057 s** |
| Peak RSS | **888.1 MiB** (gate: < 2 GiB) |
| Average cores used | **150.0 / 192** |
| Samples verified | 20,000 (1/10,000), all unique |

Against the 0.61 baseline on the same box (`427,033.53 pages/s` at 43.8 % CPU, 84.1 cores), that is
**2.22× absolute** and **+24.4 % per core** (6,317 vs 5,078 pages/s/core), with memory still under
1 GiB and CPU per page down from 196.9 µs to 158.3 µs.

The same binary on a 16-core development box reproduces **6,015 pages/s/core** — within 4.8 % of the
192-core run — so the scaling is the data plane's, not the machine's.

### 5. 📊 Seven-Domain Public Showdown, Including the Losses

Every number below is a full-set run on **one machine**, with the suite's own scorer, under a
**10 GiB memory cap** shared by PageSift and every competitor. Where we lose, the loss is printed.

Measured on Intel i7-10700 (8C/16T), 15 GB RAM, Ubuntu 26.04.

| # | Domain | PageSift 0.70 | Best competitor | Rank |
| :---: | :--- | :--- | :--- | :---: |
| **D1** | Content extraction (WCXB 2,006) | 0.6720 F1 | 0.6824 (PageSift 0.50) | 4th |
| **D3** | PDF extraction (1,403 PDFs / 7,019 checks) | **0.4506** | 0.2446 (pymupdf4llm) | **1st** |
| **D5** | RAG chunking + BM25 (472 questions) | **0.9470** R@5 | 0.9364 (semchunk) | **1st** |
| **D6** | Charset detection (3,128 files) | **0.7602** | 0.7113 (chardet) | **1st** |
| **D7** | Structured data (2,006 pages) | **0.7392** | 0.5488 (bs4+lxml) | **1st** |
| **D9** | Dynamic rendering (7 SPA scenarios) | 3/7 | 5/7 (Playwright) | 2nd |
| **D4** | DOM self-healing (2,000 mutations) | 0.8215 | 0.8875 (Scrapling) | 2nd |

**Four of seven won.** Speed where it matters: 1,403 PDFs in **0.83 s** (31× faster than pypdf,
296× faster than pymupdf4llm); 3,128 encoding detections at **11,239 files/s**; **21 MiB peak** for
structured data. Nothing came close to the 10 GiB cap — the largest competitor peaked at 1,776 MiB,
PageSift at 751 MiB.

The three we did not win, stated plainly:

- **D1** — 0.8854 precision, highest of all 17 entrants, but 0.5989 recall. WCXB's reference text
  includes boilerplate, so whole-page output scores better on this particular metric. We chose
  precision.
- **D9** — client-side and hydration SPAs render correctly, and we finish in **0.47 s vs Playwright's
  2.55 s**. We miss `setTimeout`-delayed injections because we stop at network-idle instead of
  waiting a fixed duration.
- **D4** — we beat Scrapling on adversarial decoys (100 % vs 86.4 %); the overall gap comes from a
  category where **14.6 % of the dataset's labels are wrong** (a `.price` slot contains a person's
  name).

Separately, the seven **standard** suites run earlier remain in the record:
[baselines 1–4](benchmarks/0.70_p4_step4_2_baselines_1_4.md),
[baselines 5–7](benchmarks/0.70_p4_step4_2_baselines_5_7.md), and the
[E1 stress suite](benchmarks/0.70_p4_step4_2_e1.md).

### 6. 🔧 Reliability Fixes Found by the Stress Suite

The E1 stress suite (content storm, multi-host crawl, fault storm, mixed 10-minute run) surfaced
four defects that would have hit production before they hit a benchmark:

| Defect | Fix |
| :--- | :--- |
| `fetch.timeout_secs` did not bound the wait for response headers (8 s configured → 30 s observed) | Budget now propagates to `first_byte_timeout`/`body_idle_timeout`; adaptive tuning no longer overwrites an explicit value |
| A 429 permanently widened the host's request interval (30 s cap, 1/16 decay — effectively unrecoverable) | Halve on success; honour `Retry-After` without permanently penalising the host |
| One permanently-broken URL could freeze an entire host (10 s → 600 s cooldown, unclearable) | Host-level cooldown now counts **distinct** failing URLs, with a flat cooldown |
| Runtime panicked when worker threads could not spawn under a tight `ulimit -v` | Worker count derived from available address space, halving retry, clear error |

After the fixes, the same fault-storm run converges naturally on all four hosts instead of hitting
the 480 s deadline.

### 7. ⚖️ 2.22× Over 0.61, With Less CPU Per Page

| Run | Tasks | Wall | Sustained | Cores used | Per-core | Per-page CPU | Peak RSS |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0.61 baseline (192 vCPU) | 100M | 234.2 s | 427,033 p/s | 84.1 / 192 | 5,078 | 196.9 µs | — |
| **0.70** (192 vCPU) | **200M** | **211.1 s** | **947,611 p/s** | 150.0 / 192 | **6,317** | **158.3 µs** | 888.1 MiB |
| **0.70** (16 vCPU dev box) | 100M | 1,686.1 s | 59,309 p/s | 9.86 / 16 | **6,015** | **166.2 µs** | 124.1 MiB |

**2.22× absolute throughput, +24.4 % per core, −19.6 % CPU per page.**

Per-core output on a 16-core laptop-class box (6,015 p/s/core) lands within 4.8 % of the 192-core
run (6,317 p/s/core) — the scaling is the data plane's, not a property of one machine.

0.70 also runs article-body location on every page instead of only `og:type=article` pages, which is
worth **+0.055 ROUGE-5 F1** on WebMainBench (0.5860 → 0.6414). Even with that extra work the
per-page CPU stays below 0.61: the data plane saves more than the extraction spends. Set
`PAGESIFT_NO_FORCE_ARTICLE=1` to drop the extra location pass entirely.

## 🛠️ Reproducing the 0.70 Numbers

```bash
# 1. 200M local saturation
cd bench/p0 && cargo build --release --bin p2_http_reactor_runner --bin stream_origin
bash bench/p3/run_200m_check.sh <tag>

# 2. Memory envelope (cgroup v2)
systemd-run --user --scope -p MemoryMax=768M \
  ./bench/p0/target/release/p2_http_reactor_runner \
  --formal --mode full --split-pipeline --total-tasks 50000000 --output /tmp/mem768.json

# 3. Seven standard benchmarks + E1
bash bench/scripts/e1a_sweep.sh          # content storm
bash bench/scripts/e1b_crawl.sh          # multi-host crawl
bash bench/scripts/e1c5.sh               # fault storm
bash bench/scripts/e1d_run.sh            # 10-minute mixed

# 4. Quality suites
bench/upstream/.venv/bin/python bench/p4_2_webmainbench/wceb_run.py ...
```

Full reports: [`docs/benchmarks/`](../benchmarks/) — every table above links back to a document
with the exact binaries, commit hashes, dataset checksums and scorer versions.

## 📦 Upgrade Notes

- **No API breakage.** Rust, Python, Node.js, CLI and the Firecrawl v1/v2 + Jina Reader compatible
  HTTP surface keep their shapes.
- **New config keys**: none required. `[fetch] timeout_secs` now behaves as a true per-request
  budget; if you previously relied on it being ignored for slow origins, raise it explicitly.
- **New escape hatch**: `PAGESIFT_NO_FORCE_ARTICLE=1` restores pre-0.70 extraction scope.
- **Behaviour change**: adaptive tuning no longer overrides explicitly configured timeouts.
