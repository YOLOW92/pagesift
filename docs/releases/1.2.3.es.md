## Recursos de imagen

- `imageAssets` es opcional: se indica directamente en scrape y batch, o dentro de `scrapeOptions` para crawl. Sin esta opción se mantiene la salida anterior con enlaces. `attach` conserva los enlaces Markdown y devuelve bytes Base64 como adjuntos; `embed` inserta URL de datos; `rewrite` usa referencias `asset://<id>` y adjuntos. La CLI admite `--image-assets attach|embed|rewrite` en scrape y crawl.
- El ID se deriva del SHA-256 de los bytes exportados; también se incluyen el hash completo, MIME detectado por contenido, tamaño y origen. `imageAssets` registra por imagen `ok`, `skipped-limit` o `failed` y el motivo correspondiente. La detección no se basa solo en la extensión ni en el Content-Type HTTP.
- En batch/crawl, `attach` y `rewrite` envían el Base64 de contenido idéntico una sola vez por tarea; las páginas posteriores conservan el mismo ID. En trabajos persistentes, los bytes se guardan en el almacén de adjuntos por contenido y el Base64 se reconstruye al leer la primera página. Los clientes paginados deben conservar los recursos de páginas anteriores o usar el endpoint de adjuntos mientras esté disponible. `embed` mantiene cada página autónoma y puede repetir URL de datos entre páginas.
- Las imágenes web respetan robots, límites de frecuencia, redirecciones y protección SSRF. Cada página dispone de un presupuesto de bytes, hasta 64 solicitudes, un plazo total de 10 segundos y hasta 4 descargas concurrentes. Si una imagen falla o supera un límite, se conserva el enlace original. La caché de tarea admite hasta 32 URL e imágenes de hasta 512 KiB; al reanudar un trabajo persistente se reconstruye con resultados satisfactorios. Las imágenes mayores, URL adicionales o URL distintas con el mismo contenido pueden descargarse de nuevo.
- SVG solo se admite como adjunto o referencia `asset://`, **no** como nueva URL de datos `embed`. Detectar SVG no lo sanea. Las URL de datos originales de la página se controlan por separado con `removeBase64Images`.
- Las imágenes XObject de PDF se exportan independientemente del OCR. En conversiones a PNG/TIFF, el ID se calcula sobre los bytes realmente exportados y se actualiza la referencia Markdown. Las imágenes inline de PDF quedan fuera. Los medios ZIP de DOCX/PPTX/XLSX conservan sus bytes originales; los adjuntos de imagen de correo no forman parte de este canal.
- HTTP scrape/batch/crawl devuelve los recursos. Con `--out`, la CLI escribe `images/<id>` y los resultados en `index.jsonl`. MCP scrape devuelve image content nativo. En `embed`, el Markdown con URL de datos permanece en el bloque de texto y se omite el Markdown correspondiente de structured content para evitar otra copia; el bloque de texto y el de imagen siguen duplicando los bytes.

## Flujo y compatibilidad

- `POST /v2/scrape/stream` puede enviar Markdown provisional antes de terminar las descargas y después el resultado completo. Los flujos de batch/crawl también admiten eventos provisionales con `?previews=true`. La vista previa tiene un máximo de 1 MiB, puede descartarse y no se guarda ni se reproduce; los ID y la reanudación de páginas finales no cambian. El JSON normal espera a que termine el procesamiento de recursos.
- Ahora se acepta `removeBase64Images: false` y se conservan las imágenes data URL originales; el valor predeterminado `true` sigue eliminándolas. Las claves de caché distinguen ambas opciones.
- `exportImages` sigue disponible. El JSON del primer adjunto en los modos nuevos incluye MIME, `data` Base64 y el indicador `inlineData`. Consulta la [guía de recursos de imagen](../image-assets.md).

## Base64 propio y comparación de tres implementaciones

- `pagesift-base64` incorpora alfabetos estándar y URL-safe, relleno opcional, decodificación estricta o tolerante a espacios, decodificación en flujo y creación de data URL con una sola reserva. AVX2/NEON se detectan en ejecución, con alternativa escalar. CDP, MCP, autenticación de proxy y recursos de imagen usan el nuevo crate; Office MIME conserva su decodificador anterior, más permisivo.
- La comparación en el mismo proceso usa PageSift, `base64` 0.23.1 y `base64-simd` 0.8.0 en un Intel i7-10700. Para 1 MiB estricto, la codificación tardó **57.8714 / 422.6966 / 102.6861 µs** y la decodificación **55.0611 / 502.2591 / 135.9397 µs**, respectivamente; menos es mejor. Con 8 bytes, la codificación estricta fue **0.0110 / 0.0090 / 0.0073 µs**, por lo que PageSift no ganó en todos los tamaños.
- La [comparación completa](1.2.3-benchmarks.md) presenta los 13 tamaños para codificación y decodificación estrictas y decodificación tolerante a CRLF, con condiciones, diferencias en entradas pequeñas y distintas reglas de tolerancia. Es una microprueba con búferes calientes en una máquina, no una medición integral de scraping.
- Las técnicas AVX2 estudiadas de MoeForge/moego se reconocen en [`THIRD-PARTY.md`](../../crates/pagesift-base64/THIRD-PARTY.md). NEON en ARM se comprobó mediante compilación cruzada; la comparación no se ejecutó en hardware ARM.
