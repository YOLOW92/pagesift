# PageSift 1.2.3 Release Notes

> **Version:** `v1.2.3` · **Date:** 2026-11-09 · **License:** AGPL-3.0-only; commercial licensing available

Changes since 1.2.2. Also available in [简体中文](1.2.3.zh-CN.md), [日本語](1.2.3.ja.md), and [Español](1.2.3.es.md).

## Image assets

- `imageAssets` is opt-in on scrape and batch requests, or inside `scrapeOptions` for crawl. Omit it to retain the previous link-only output. `attach` keeps Markdown links and returns Base64 attachment bytes; `embed` writes data URLs into Markdown; `rewrite` uses `asset://<id>` references and returns attachments. The CLI supports `--image-assets attach|embed|rewrite` on scrape and crawl.
- Assets report an ID derived from the SHA-256 of exported bytes, the complete hash, detected MIME type, byte count and source. The separate `imageAssets` outcomes include `ok`, `skipped-limit` and `failed`, with a reason when relevant. Image recognition uses content, not just filename extensions or HTTP Content-Type.
- `attach` and `rewrite` publish identical bytes once per batch/crawl task. Later pages keep the same asset ID without another Base64 payload. With persistent jobs the asset bytes are stored in the content-addressed attachment store; the first page's inline payload is reconstructed when that page is read. Pagination clients should retain assets from earlier pages or use the attachment endpoint while available. `embed` instead keeps each page self-contained, so data URLs may repeat across pages.
- Web images use the existing robots, rate-limit, redirect and SSRF policy. Each page has a byte budget, up to 64 image requests, a 10-second image deadline and at most four concurrent image fetches. Fetch failures and limit skips retain the original links. A bounded task-local cache shares up to 32 URLs with images up to 512 KiB; persistent job recovery repopulates it from saved successful sources. Larger images, additional URLs or different URLs with identical bytes can still require repeated downloads.
- SVG is allowed as an attachment or `asset://` reference, **not** as a new `embed` data URL. Identifying SVG does not sanitize it. Source-page data URLs are governed separately by `removeBase64Images`.
- PDF XObject images use the asset pipeline independently of OCR. IDs hash the actual exported bytes, including images converted to PNG/TIFF, and PDF Markdown references follow the exported ID. PDF inline images are not included. DOCX, PPTX and XLSX ZIP media preserve their original bytes; email image attachments are not included in this pipeline.
- HTTP scrape, batch and crawl return the asset data. With `--out`, CLI output writes `images/<id>` and includes outcomes in `index.jsonl`. MCP scrape returns image assets as native image content. In MCP `embed` mode, Markdown with data URLs is kept in the text block but omitted from structured content to avoid a further copy; native image blocks still duplicate the bytes present in the text.

## Streaming and compatibility

- `POST /v2/scrape/stream` can send provisional extracted Markdown before image downloads complete, followed by the final scrape result. With `?previews=true`, batch/crawl streams also emit provisional Markdown before their final page events. Previews are limited to 1 MiB, may be dropped, and are not replayed; final page sequence IDs and resume behavior are unchanged. Normal JSON results still wait for asset processing.
- `removeBase64Images: false` is now accepted and preserves source-page data URL images in Markdown; the default `true` continues to remove them. Cache keys distinguish the two options.
- Existing `exportImages` remains available. New-mode attachment JSON contains MIME, Base64 `data` for the first published copy and an `inlineData` marker. HTTP, CLI, MCP and stream details are in the [image asset guide](../image-assets.md).

## Base64 implementation and measurements

- `pagesift-base64` provides standard and URL-safe alphabets, optional padding, strict and whitespace-tolerant decoding, streaming decoding, and a single-allocation data URL encoder. AVX2 and NEON paths use runtime detection; scalar fallbacks remain. CDP data URLs and screenshot decoding, MCP blobs, proxy authentication and the image-asset pipeline use the new crate. Office MIME keeps its existing more permissive decoder.
- A three-way same-process comparison measured PageSift, `base64` 0.23.1 and `base64-simd` 0.8.0 on an Intel i7-10700. For 1 MiB strict input, encoding took **57.8714 / 422.6966 / 102.6861 µs** and decoding **55.0611 / 502.2591 / 135.9397 µs**, respectively; lower is better. At 8 bytes strict encoding took **0.0110 / 0.0090 / 0.0073 µs**, so the new implementation was not fastest for every size.
- The [complete comparison](1.2.3-benchmarks.md) lists all 13 sizes for strict encoding/decoding and CRLF-tolerant decoding, including measurement procedure, mixed small-input results and the difference in tolerant-decoding semantics. These are warm-buffer measurements on one machine, not an end-to-end scrape benchmark.
- AVX2 techniques studied from MoeForge/moego are credited in [`THIRD-PARTY.md`](../../crates/pagesift-base64/THIRD-PARTY.md). ARM NEON was cross-checked by compilation; the recorded comparison was not run on ARM hardware.

## Validation

Release-mode tests covered the affected network, API, engine, sink and MCP crates, with targeted tests for CLI output, MCP image content, PDF/Office media, shared budgets, gzip expansion, streaming previews, concurrent deduplication, restart, webhook retries, storage failure and mirror replay. `cargo deny --config .github/deny.toml check` passed.
