## E1-A 内容处理风暴

| **唯一合计** | **13,661** |

HTML 总量 1.74 GB。重复内容只保留一份，**不把重复样本算作新增样本**。

### A-3 结论（与既有 P3 数字的差异，必须说明）

**真实网页正文抽取在 32 线程达到峰值，之后随线程数单调下降**（9,168 → 6,520，−29%）。
单页成本约 1.4 ms，工作时集是 DOM 与字符串分配，属**内存带宽/分配器受限**，不是 CPU 受限。

这与 192 核上合成页的饱和吞吐不矛盾：那一轮是 5 类确定性 fixture、
结构简单、工作集小；这里是跨 4 个真实数据集的复杂 DOM。
**结论：192 核的饱和度不能从合成 fixture 外推到真实网页。**

## E1-C 故障与防御风暴

**故障注入**：固定种子 `e1-2026`，按 `sha256(seed + url)` 决定是否注入及注入类型
（429 / 503 / slow 2.5 s / truncated / malformed / timeout 30 s），同一 seed 下每次运行故障集合完全一致。
密度：h1 **0%**（对照）、h2 **10%**、h4 **30%**。

### C-1 完成度（单请求超时 8 s，整轮 480 s 硬上限）

| 主机 | 故障密度 | 完成页数 | 结论 |
| :--- | ---: | ---: | :--- |
| h1 | 0% | **245 / 245** | 完整 |
| h2 | 10% | **180 / 245** | 未完成 |
| h4 | 30% | **61 / 245** | 未完成 |

**故障密度越高，完成度越低（245 → 180 → 61）**，且未能在时限内排空。
未完成如实计入，没有延长时限凑数。

### C-2 安全与防御不变量（全部守住）

| 不变量 | 结果 |
| :--- | :--- |
| robots 禁止路径（`/private/`）从未被抓取 | ✅ |
| 302 到私网地址（`/go-private`）未被跟随 | ✅ |
| 重定向环（`/r/loop`）有界，未无限展开 | ✅ |
| 意外错误码 | **0**（只出现 `TIMEOUT` 与 `RATE_LIMITED` 两类预期拒绝） |

预期拒绝计数：`TIMEOUT 10`、`RATE_LIMITED 10`；无任何泄漏到调用方的 panic 或未知错误。

### C-3 根因：`timeout_secs` 只覆盖读 body，**不覆盖等待响应头**

逐端点隔离测量（`timeout_secs = 8`）：

| 端点 | 耗时 | 结果 |
| :--- | ---: | :--- |
| `/fault/429` | 0.1 s | `RATE_LIMITED` ✅ |
| `/fault/503` | 0.1 s | 正常回退 ✅ |
| `/fault/slow`（2.5 s） | 2.6 s | 等到响应 ✅ |
| `/fault/truncated` | **8.0 s** | `TIMEOUT`，被 8 s 上限截断 ✅ |
| `/fault/malformed` | 0.1 s | 容错通过 ✅ |
| `/fault/timeout`（服务端睡 30 s） | **30.1 s** | ❌ **未受 8 s 上限约束** |
| `/r/loop` | 0.0 s | `UPSTREAM_ERROR`，有界 ✅ |
| `/go-private` | **10.0 s** | 未跟随，但耗时超预期 ❌ |

**这就是 E1-C 卡住的根因**：服务端迟迟不发响应头的场景，请求会一直等到服务端自己超时（或传输层超时），
`fetch.timeout_secs` 未生效。截断响应因为进入读 body 阶段，反而被正确截断在 8 s。
Go-private 的 10 s 同理（重定向后等待头）。

### C-4 内存约束：不降级，直接挂死

`ulimit -v 262144`（256 MiB 地址空间）下爬取：**600 s 内输出 0 页、无任何错误输出、进程 CPU 0%**。
即**内存受限时不优雅降级、也不报错，而是挂起**。

### C-5 中断恢复：没有检查点

跑到一半 `kill -9`，再对同一主机重跑：

| 指标 | 值 |
| :--- | ---: |
| 中断轮已输出 | 120 |
| 续跑轮输出 | 180 |
| 完整参照（同主机无中断） | 245 |
| 两轮重叠 URL | **120（全部重抓）** |
| 跨轮重复输出 | **120** |
| 相对完整参照仍缺 | **65** |

**结论：`crawl` 没有断点续传。** 重启后从头再来，已抓过的 120 个 URL 全部重复抓取，
且在同一时限内仍留 65 个空洞。任务要求的「零重复、零空洞、零伪完成」在本实现下**不成立**。

### D 的诚实结论：本轮**没有把 192 核压满**

CPU 全程只有 **0.01–0.41 核**。原因有二：

1. **A（内容处理风暴）太快**：13,661 页在 32–160 线程下 1.5–2.1 秒就跑完，占不到 10 分钟窗口的 1%。
2. **B/C 被源站限住**：源站是单进程 Python `ThreadingHTTPServer`，受 GIL 约束，
   吞吐远低于 PageSift 能消耗的速度。爬取阶段时间几乎全花在等源站，CPU 接近空闲。

因此 E1-D 测到的是「混合场景下能跑完什么、会留下多少未完成与重复」，
**不是**「192 vCPU 可持续混合压力」。要满足后者需要：
（a）A 全程循环供料而非跑一遍；（b）源站改为多进程并按任务要求**独立 CPU 集**；
（c）把源站自身 CPU 计入成本。本轮的配置不含以上三项，因此 E1-D 的定位是
「混合场景下能跑完什么、会留下多少未完成与重复」，而非核数压满。

## E1-C 修复后的复测（同一测试床、同一故障种子）

E1-C 暴露的问题已定位并修复，同一配置重测（`timeout_secs = 8`，480 s 时限，四个主机并发）：

| 主机 | 配置 | 修复前 | 修复后 |
| :--- | :--- | :--- | :--- |
| h1 | 无故障、无 delay | 245 页完成（2.6 s） | **245 页完成（2.44 s）** |
| h2 | 10% 故障、无 delay | 157–183 页，**撞 480 s 上限未完成** | **192 页 / 17 错误，240 s 自然结束** |
| h4 | 30% 故障、无 delay | 55–62 页，**撞 480 s 上限未完成** | **140 页 / 20 错误，253 s 自然结束** |
| h5 | 无故障、`Crawl-delay: 1` | 242–245 页 | **245 页，245.33 s（1.00 s/页）** |

修复后**没有任何一台上限被撞**，全部自然收敛。h2/h4 未到 245 页是因为被注入故障的页面本身不可抓，
且它们的父页面失败会连带截断发现链（192+17=209、140+20=160），属预期。

### 三处修复

1. **`timeout_secs` 现在覆盖等待响应头**
   `crates/pagesift/src/config.rs`：`timeout_secs` 除了写 `total_timeout`，同时收紧
   `first_byte_timeout` / `body_idle_timeout` / `connect` / `dns` / `tls` / `tail_threshold`，
   并置 `timeouts_explicit = true`。
   `crates/pagesift/src/adaptive.rs`：`apply_to_config` 在该标记为真时**不再覆盖**超时字段——
   之前自适应会把用户设的 8 s 直接改回 30 s。
   实测：`/fault/timeout` 30.1 s → **8.03 s**；`/go-private` 10.0 s → **8.03 s**；正常页 0.07 s 不受影响。

   > 尝试过在 `fetch.rs` 把总预算套在 `transport.get()` 外层，但那会把**排队时间**算进超时，
   > 高并发下大量请求还没发出就被判超时（h2 降到 42 页）。已撤回，改用配置层收紧——
   > `first_byte_timeout` 原本就在取得容量之后才开始计时。

2. **主机级冷却不再被单个坏 URL 触发**
   `crates/pagesift-policy/src/backoff.rs` 新增 `on_url_failure(host, url)`：
   按**不同 URL** 计数，同一 URL 重试不再累加；触发后冷却固定为 `base_cooldown` 并清零重计。
   DNS/上游错误仍走主机级、可指数增长的 `on_failure`。

3. **限流后的请求间隔可以恢复**
   `crates/pagesift-policy/src/limiter.rs`：`PENALTY_DECAY` 由 16 改为 2（每次成功减半）。
   `crates/pagesift-policy/src/policy.rs`：服务端给了 `Retry-After` 时只按它冷却，**不再同时**
   永久加大整站请求间隔。
   修复前：10% 的 429 会把该主机间隔推到 30 s 上限，从上限恢复需上百次成功，等同永久降速——
   这才是 E1-C 早期「越跑越慢」的主因（不是超时）。

`pagesift-policy` 新增 `one_sticky_bad_url_does_not_freeze_the_host`；
非 CDP 全工作区 **684 个测试通过、0 失败**。
（`pagesift-cdp` 的 13 个浏览器测试在本沙箱内因浏览器无法启动而失败，与本轮改动无关。）
