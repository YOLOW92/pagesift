> 环境：Google Cloud `c4-highcpu-192`，192 vCPU，4 NUMA 节点  
> 生成时间：2026-10-24 12:00:43 UTC  
> 原始数据：[`benchmarks/scale/results/scaling_cores_192.csv`](../../benchmarks/scale/results/scaling_cores_192.csv)

## 方法

- 阶梯：`[1, 2, 4, 6, 8, 12, 16, 20, 24, 28, 32, 36, 40, 48, 56, 64, 72, 80, 88, 96, 104, 112, 120, 128, 144, 160, 176, 184, 192]`；每档扫描并发比 `alpha=[4, 8, 12, 16, 20, 24, 28, 32, 40, 48, 64]` 与 1/8、1/4、1/2 核心比例等分片粒度。
- 合成源站与 PageSift runner 同时绑定到相同 CPU 集合；96 线程前优先使用物理核，之后加入 SMT sibling。
- 第一阶段对完整扩展网格各实测一次；第二阶段对每个核心档前 3 名配置补测至 3 次并取中位数。
- 单次任务量随核心数增长，避免高核点短跑失真。
- CPU 指标只使用 Rust Runner 自身 `/proc/self/stat` 的 `utime + stime`，不包含合成源站、其他进程或系统 CPU 时间，并按 Runner 的 CPU 亲和性容量归一化。
- 完成前写入 `.partial.csv`，全部点结束后才原子替换正式 CSV；不稳定点保留失败数并从最优候选中排除。

## USL 拟合

`QPS(N) = gamma*N / (1 + sigma*(N-1) + kappa*N*(N-1))`

- gamma = **8631.843 pages/s/core**
- sigma = **0.01340730**（1.34073%）
- kappa = **0.0000000000**（0.0000000%）
- R² = **0.838813**
- 理论拐点 N* = **316967988.34 vCPU**，QPS* = **643,816.6 pages/s**

## 数据完整性与不稳定点

- 正式 CSV 共 **3,109** 条数据记录：`compact` 主扫描与确认记录 3,067 条，拓扑对照记录 42 条。
- `compact` 完整覆盖 **29** 个核心档；`numa_spread`、`single_socket`、`single_numa` 分别完成 18、12、12 条对照记录，且拓扑对照全部 `failed=0`。
- 3,109 条记录的 `process_cpu_time_s` 均为有限正数；CPU 时间只来自 Runner 自身 `/proc/self/stat` 的 `utime + stime`。
- 稳定记录 1,421 条；`failed>0` 的不稳定记录 1,688 条，涉及 **1,686 个唯一配置**，不稳定记录占 54.29%。它们作为调度与过载边界证据保留，但不参与正式最优候选评选。
- 87 个三次确认组中有 5 组至少一次出现失败请求；聚合时以组内最大 `failed` 判定稳定性，因此这些确认组被整体排除。最终 29 个核心档的正式最优候选，其三次重复均为 `failed=0`。

## 关键结论

1. **正式吞吐峰值位于 112 vCPU。** `38 shards / alpha=8` 的三次确认中位数为 **522,280.3 QPS**，Runner CPU 利用率 81.3%，折合约 91.1 个满载逻辑 CPU，峰值 RSS 188.8 MB，队列 P99 为 0.323 ms。
2. **24 至 96 vCPU 存在明显的 NUMA 调度平台期。** 24 vCPU 已达到 213,737.3 QPS；28 至 64 vCPU 只缓慢增长至约 231k QPS，80 至 96 vCPU 又回落在约 228k 至 230k QPS。进程 CPU 时间与现场逐核观测共同表明，很多配置长期集中在单个 24 物理核 NUMA 域，而不是均匀使用全部亲和性 CPU。
3. **104 至 144 vCPU 出现调度相变，而非平滑线性扩展。** 104、112、128、144 vCPU 的正式结果分别达到 499k、522k、474k、482k QPS；这说明特定分片与并发组合能够突破单 NUMA 域局部性，但该状态对参数敏感。
4. **局部性优先于盲目跨 NUMA 均匀分布。** 48 vCPU `single_numa` 比同档 `compact` 高 24.86%；96 vCPU `single_socket` 高 71.80%。相反，24/48/72 vCPU 的 `numa_spread` 分别低 69.27%、44.16%、36.83%。在当前本机回环源站模型下，强制跨节点分散会放大唤醒、缓存和内存访问成本。
5. **SMT 并未带来持续收益。** 112 vCPU 后吞吐整体回落；192 vCPU 为 423,898.9 QPS、Runner CPU 42.5%，与 P0 的 192 vCPU 饱和特征接近。高核心数本身不能修复调度局部性。
6. **单一 USL 曲线只能作为总体描述，不能用于可信外推。** 本次拟合 R² 为 0.838813，但 `kappa` 被优化到接近零，导致理论拐点约 3.17 亿 vCPU，显然没有工程解释力。数据跨越单 NUMA、跨 Socket 和 SMT 多种离散拓扑状态，不满足同一平滑 USL 曲线的同质性假设；P2 应以分段拓扑模型和运行期测量为依据。

## 对 P2 的约束

- 调度器必须识别 Socket、NUMA 节点、物理核与 SMT sibling，不能只读取逻辑 CPU 数量。
- 优先在单 NUMA 或单 Socket 内形成完整工作组，再通过独立节点工作组扩展；不要把任务线程简单 round-robin 到所有 NUMA 节点。
- Runner 与本机合成源站需要拆分 CPU/NUMA 资源，避免共享亲和性集合造成回环唤醒与源站竞争混入扩展曲线。
- 自适应策略必须把 `failed>0` 作为硬性淘汰条件，并使用多次确认而非单次高峰决定分片与并发参数。
- 112 vCPU 的 522k QPS 是本阶段的稳定标定峰值，不是 P3 的最终架构上限；P2/P3 应重新验证 100M 长跑、跨 NUMA 稳态和真实 CPU 激活率。
