# 0.89 — `pagesift-cluster`: single-host and multi-server coordination

New crate `crates/pagesift-cluster`. The first sections cover the crate and its module tests; "Service roles"
covers how `pagesift serve --role gateway|worker|standby` uses it.

## What the crate contains

| Module | Content |
|---|---|
| `coordinator.rs` | `Coordinator<A>` trait (submit, pull, renew, commit, cancel, owner_of, publish_stats, priors), `Deliver<A>` result sink; on the worker side `A: Into<Vec<u8>>` |
| `local.rs` | `LedgerFront<A>` (`LocalCoordinator<A>`): `Coordinator` on top of the ledger, used by the single host and inside the gateway; single-host results are handed over by ownership (no serialization) |
| `gateway.rs` | `GatewayCoordinator`: sessions, host-map push, journal shipping to the standby, eviction of silent workers |
| `remote.rs` | `RemoteCoordinator<A>`: worker side over the frame protocol; local HRW copy; politeness hand-off (`SiteStates`) |
| `standby.rs` | `Standby`: replays the shipped journal, detects primary loss, takes over with `term+1` |
| `ledger/` | `Ledger`, shared by local and gateway: tasks, leases, fencing, idempotent commit, cancel, membership, site pause, stats hub, replay |
| `journal.rs` | Ledger change log in a `pagesift-store` append-only list; used for crash recovery and for log shipping |
| `hrw.rs` | Weighted rendezvous hashing for site affinity |
| `stats.rs` | `StatsHub`: merge of `pagesift_stat` tables, de-duplication by sequence number, priors per scope |
| `codec.rs` | `Codec` trait for field types and `codec_enum!`, one table (tag → variant {field: type}) that generates both the enum and its encoder/decoder; used by frames and journal records |
| `frame.rs`, `transport/` | Frame format, HTTP/2 stream (h2c / TLS / mutual TLS), token auth, version negotiation |

Third-party crates: none new. The crate uses `hyper` 1.12 (client, server, http2), `hyper-util` 0.1.21,
`http-body` 1.1, `http-body-util` 0.1.5, `bytes`, `tokio`, `tokio-rustls` 0.26 (ring), `blake3`, all already
in the workspace. Dependencies on other pagesift crates: `pagesift-stat`, `pagesift-store`. Appended (no existing

## Protocol

- One HTTP/2 connection per worker, opened by the worker. `POST /pagesift-cluster`; the request body is the
  worker-to-gateway frame stream, the response body the gateway-to-worker stream.
- Headers: `authorization: Bearer <token>`, `pagesift-worker: <id>`, `pagesift-cluster-version: <min>-<max>`.
  The gateway picks the highest version in the intersection and echoes it, or answers 400 (no common version)
  / 401 (bad token) with the reason in `pagesift-cluster-error`. Supported range in this build: 1–1.
- Frame: `[u32 LE length][u8 type][u64 LE correlation id][payload]`. Correlation id 0 marks pushes
  (`HostMap`) and one-way messages (`Stats`, `Handoff`). Payload encoding is `pagesift_stat::{Writer, Reader}`
  (fixed-width little-endian integers and floats, length-prefixed byte strings). Default frame limit: the store's
  default segment size (64 MiB), because a result is journaled together with its completion mark in one record.
- Journal record: `[u8 version = 4][u64 term][u8 type][fields]`; types `Submit` (with an optional account),
  `Grant`, `Done`, `Cancel`, `Stats`, `Term`, `Reserve`, `Settle`, `Release`, `Request`, and the snapshot section
  `SnapBegin`, `SnapTasks`, `SnapDone`, `SnapQuota`, `SnapStats`, `SnapEnd`. Frames and journal records share the field encoding in `codec.rs`.
- Messages: `Hello`, `Welcome`, `Pull`, `Granted`, `Renew`, `Renewed`, `Commit`, `Ack`, `Submit`, `Submitted`,
  `Cancel`, `Cancelled`, `Stats`, `PriorsReq`, `Priors`, `Handoff`, `HostMap`, `Ship`, `Records`.
- Transport: h2c with prior knowledge, or TLS via rustls with ALPN `h2`; optional client-certificate
  verification against a deployer-supplied CA. Token auth applies in all cases. The gateway stores only
  `blake3::derive_key("pagesift-cluster 2026-11 worker token v1", token)` per worker; tokens can be revoked
  individually.

## Leases and fencing

- Fencing token = `(term, epoch)`. `epoch` is incremented on every (re)assignment of a task, `term` on every
  restart or standby takeover. A commit or renewal is accepted only when its token equals the ledger's current
  assignment for the task. A commit whose lease expired but was not yet reassigned is
  still accepted (nobody else holds the task); renewing such a lease re-grants it to the caller.
- Duplicate commit of the same token returns `Ok` and does not deliver the result again. Completion records are
  kept for the longest lease issued by the shard, then pruned.
- Lease length = upper `1−δ` confidence bound of `q(1−δ)` of the task class's run time (order-statistic bound,
  Conover 1999 §3.2, over a DDSketch) + upper bound of the worker's RTT `q(1−δ)`. Until the bound exists
  (at δ = 0.05 that needs about 87 samples) the task's own `timeout` is used. Shards pool samples into the
  global table every `⌈ln δ / ln(1−δ)⌉` = 59 completions.
- Renewal time = `ttl − 2·rtt_hi` (one one-way trip for the grant, one for the renewal); in process
  (`rtt_hi = 0`) `ttl/2`.
- Cancel: queued tasks are removed; running ones are told `Cancel` on their next renewal; a later commit is
  refused with `Cancelled`.

## Site affinity

- Weighted HRW (Thaler & Ravishankar 1998; logarithmic weighting from Schindelhauer & Schomaker 2005),
  score `w / −ln u`, `u` from a SplitMix64 mix (`pagesift_stat::rng::splitmix64`) of the site key and the member key (BLAKE3 of the worker id).
- When ownership of a site changes, the gateway pauses the site until (a) the previous owner's leases on that
  site have expired and (b) one RTT bound of the previous owner has passed if it is still a member. When the
  previous owner sends `Handoff{site, wait, state}`, the pause becomes `now + wait` (never earlier than its
  outstanding leases) and the state rides on the next lease for that site. Each shard keeps the set of in-flight
  leases per site, so computing a site's pause looks only at that site's leases.

## Warm standby

- The standby connects to the primary and sends `Ship{from}` as its first frame (a worker's first frame is `Hello`). The primary streams
  `Records` batches from its journal as they are appended and an empty batch every `heartbeat`
  (default 1 s) when idle.
- Loss detection: the standby keeps a DDSketch of inter-arrival gaps that end in a heartbeat. The limit is the
  upper confidence bound of `q(1−δ)` of those gaps, never below the heartbeat interval; before the bound exists,
  twice the larger of the heartbeat and the largest gap seen.
- Takeover writes a `Term` record with `term+1` and restarts all outstanding leases on the new clock. Records
  shipped with a lower term are refused, leases issued by the old primary after the takeover carry the old term
  and are refused, and a worker that has seen the new term refuses to connect to a gateway with a lower one.

## Choices and reasons

| Alternative | Implemented | Reason |
|---|---|---|
| Standby pulls new store segments (physical log shipping) | Ships the ledger's logical journal records | Replay uses the same `apply` as the live path and the crash-recovery path; no new segment-level read API in `pagesift-store` is needed; the standby's store ends up with the same journal and can itself serve a standby |
| Gateway lease timeout = `q(1−δ)` of heartbeat intervals | Same quantile, measured on the standby side from gaps ending in a heartbeat, floored at the heartbeat interval | Gaps between data batches are much shorter than heartbeats and would pull the quantile below the heartbeat interval |
| Worker liveness by heartbeat | Connection lifetime, plus: a worker whose lease expires without it having sent any frame since that lease was granted or renewed is evicted | No separate liveness timer; workers that are working renew or pull, idle workers hold no lease |
| `Lease{task, epoch, expires}` | `Lease{task, epoch, term, expires, ttl, received, renew_after, work, handoff}` | `term` is required to fence writes from an old gateway; `received` (local time the lease was obtained) gives the run time reported on commit; the rest is what the worker needs to execute and renew |
| Core types in `pagesift-flow` | `Lease`, `Resources` (= `pagesift_stat::decide::Cost`) defined here | `pagesift-flow` has no such types; the crate therefore does not depend on `pagesift-flow` |
| A fixed result type | Generic `A`; `Vec<u8>` on the wire | The crate does not depend on a particular result type |

## Quotas, rate limits and fair scheduling

- Daily page quota per account lives only in the ledger as appended records: `Reserve{hold, account, day,
  amount, task}`, `Settle{hold, actual}`, `Release{hold}`. The day is the UTC day number (Unix ms / 86 400 000).
  Balance = daily limit − settled − open reservations for that day, summed from the records, so a restart or a
  standby replay gives the same balance. Interface on `Ledger`: `set_limits(account, AccountLimits)`,
  `reserve(account, amount) -> Result<Hold, Refusal>`, `settle(&Hold, actual)`, `release(&Hold)`,
  `balance(account) -> Option<u64>` (`None` = no limit). An account without a limit gets a hold with `id == 0`
  and nothing is recorded. A refusal carries the limit and the time to the next UTC midnight.
- Tasks submitted with `submit_as(task, Some(account))` reserve one page when they are granted. The hold is
  settled on commit and released when the lease expires or the task is cancelled; a requeued task reserves again
  at its next grant. An account with no balance left is not granted tasks. After a restart or takeover, holds of
  tasks that are done are settled and holds of tasks that are not leased are released (a crash between the two
  records).
- Requests per minute: in-memory token bucket per account (capacity = requests per minute, linear refill). Every
  admitted request appends `Request{account, at}` (wall-clock ms). An account without a bucket (after restart or
  takeover) gets one rebuilt from the requests of the last minute, starting from a full bucket one minute ago.
  Interface: `check_rate(account) -> Result<(), Refusal>`.
- Fair scheduling between accounts: weighted deficit round robin (Shreedhar & Varghese 1995) in `pull`, one grant
  per visit, quantum `wᵢ / min w` with `wᵢ` = the account's daily page limit. Accounts without a limit and tasks
  without an account use the largest configured limit as weight (1 when none is set). Per shard the queues are
  keyed by (site, account) and the ready lists by (owner, account). Each pulling thread keeps its own round-robin
  state (deficits in a thread-local map), so a pull writes no shared state for scheduling; every thread grants in
  proportion to the quanta, hence so does their sum. Accounts and weights are registered in a global table that is
  written only when a new account appears or a weight changes; threads resynchronise when its generation number
  changes. While no task has carried an account, `pull` takes the path without the scheduler.
- Limits are configuration, not journal state: the standby has to be given the same limits.

## Journal checkpoints

- A snapshot is a section of records `SnapBegin{task_hw, hold_hw}` … `SnapEnd` holding the whole ledger state:
  tasks (state, last fencing token, holder, account), completion records kept for duplicate detection, open holds,
  settled usage per (account, day), the last minute of admitted requests, merged stats tables and the sequence
  numbers seen per origin. `task_hw` and `hold_hw` keep task and hold ids from being reused. Records are split so
  that each is at most half the frame limit, the same rule as a shipping batch.
- After `SnapEnd` the journal head below `SnapBegin` is dropped. Replay reads from the first live record and loads
  a snapshot only into an empty ledger; a snapshot met with state already current (a standby in sync, or a crash
  between writing a snapshot and trimming) is skipped. A snapshot section without `SnapEnd` (crash while writing)
  is ignored because the previous snapshot is still the head.
- When: as soon as the bytes appended since the last snapshot exceed the size of the last snapshot. Each byte of
  ordinary journal pays at most one byte of snapshot (write amplification ≤ 2) and the live journal is at most one
  snapshot plus one snapshot's worth of increments. The snapshot holds every shard, quota and stats lock in the
  same order as the live paths; the pause is proportional to state size and amortised by the rule above.
- In the snapshot, admitted requests are merged per second and stamped with the end of their second. A later
  consumption time leaves fewer tokens after the capacity cap, so the rebuilt bucket is never fuller than one
  rebuilt from individual records. Between snapshots each admitted request is still one record: a count written
  later would be lost in a crash and make the rebuild more lenient.
- The standby trims its own journal at the same index when it applies `SnapEnd`. A standby whose next index has
  been trimmed on the primary receives the primary's latest `SnapBegin` at a higher index, clears its state and
  journal, shifts its journal's index base to that index (kept in the store's KV) and loads the snapshot.
- Replayed stats deltas whose kind is registered only after the ledger is opened are kept and merged at
  registration.

## Service roles

`pagesift serve --role <role>` (or `role` in `[cluster]`; the command line wins). Without a `[cluster]` section
the role is `standalone`. `all` is accepted as another name for `standalone`.

### Configuration: `[cluster]`

| Key | Used by | Meaning |
|---|---|---|
| `role` | all | `standalone` (default), `gateway`, `worker`, `standby` |
| `id` | worker, standby | Identity in the cluster; tokens are registered under it and HRW uses it |
| `token` | worker, standby | Pre-shared token, a plain value or `{ env = "VAR" }`. A worker logs the token's hash at start |
| `listen` | gateway, standby | Address for worker connections (a port separate from the HTTP API) |
| `gateways` | worker | Gateway addresses, tried in order (primary first, then standby) |
| `primary` | standby | Address of the primary gateway |
| `standby` | gateway | Id of the standby (its token is registered under `[[cluster.workers]]`); turns the journal on |
| `journal` | gateway | Write the ledger journal into the data directory's store (compacted by the ledger's snapshots). Default: on when `standby` is set, else off |
| `mcp_port` | gateway, standby | MCP over HTTP on 127.0.0.1:`mcp_port`, served by the gateway process; not started when absent |
| `h2c` | all | Plain-text HTTP/2; must be set explicitly, conflicts with `[cluster.tls]` |
| `[cluster.tls] cert`, `key` | gateway: server certificate; worker: client certificate for mutual TLS | PEM files |
| `[cluster.tls] ca` | worker, standby | CA that signs the gateway certificate; default: system roots |
| `[cluster.tls] client_ca` | gateway | Require and verify worker certificates (mutual TLS) |
| `[cluster.tls] server_name` | worker, standby | Name on the gateway certificate; default: host part of the address |
| `[[cluster.workers]] id`, `token_hash` | gateway, standby | Allowed workers and standbys; only the BLAKE3 token hash is stored |

### Role behaviour

- **standalone**: the code path of 0.81–0.88. Pages are scraped in process by `Scraper`; nothing is encoded,
  no ledger, no frame protocol. It does not go through `LocalCoordinator`: `Task.body` is a byte string, so
  routing in-process pages through the ledger would encode every request. Quotas and request rates use the
  in-process token bucket and the per-day usage record in the store, as before.
- **gateway**: serves the same HTTP API (Firecrawl-compatible routes, jobs, streaming, webhooks unchanged).
  The engine behind the router is `ClusterEngine`:
  - `/v2/scrape` and every page of a batch scrape are submitted as a task to `GatewayCoordinator`;
  - crawls keep their frontier, de-duplication, URL-rewrite/trap learning, scope and focus scoring on the gateway
    (single writer); each page fetch of the crawl is a task (`Scraper::route_pages`), and the worker returns the
    document with its links, from which the gateway de-duplicates, scores and enqueues;
  - map, search, extract and `/v2/parse` run on the gateway;
  - robots mode is decided on the gateway (request type and `allow_crawl_ignore_robots`) and carried in the task;
  - per-key requests per minute and pages per day are kept in the ledger (`Ledger::check_rate`, `reserve` +
    `settle`); all accounts are registered with `Ledger::set_limits` when the router is built;
  - with `mcp_port`, the MCP tools (scrape, map, crawl, batch) use the same `ClusterEngine`;
  - admission: each worker reports its `Engine::admitted_concurrency()` (the limiter's current global target) in
    every `Pull` frame (`capacity`; the handshake weight until the first pull). The ledger keeps the latest value per
    member (`Ledger::set_capacity`, `Ledger::capacity`); a worker that leaves the host map is removed. The gateway's
    `Scraper::concurrency()` and `ClusterEngine::admitted_concurrency()` return that sum (at least 1), so crawl
    in-flight limits and batch concurrency follow the online workers. The HRW weight stays the handshake value, so
    site ownership does not move when admission changes.

  Task body and result are `[u64 request number][pagesift_sink::codec payload]`. The gateway registers the
  request number before submitting, the worker echoes it, and `Deliver` hands the result to the waiting
  request; results with an unknown number (an earlier run, a cancelled request) are dropped. A request that is
  dropped before its result arrives (job cancelled, client gone) cancels its ledger task. The gateway opens a
  second listener for workers (`GatewayCoordinator::serve` per connection, h2c or TLS) and runs
  `run_ticker()` in the background. Task class = requested engine (`http`, `browser`, other); task timeout =
  the request's `timeout`, else the fetcher's total timeout.
- **worker**: no HTTP API. Connects to the first reachable gateway (`RemoteCoordinator::connect`, with the
  highest term seen so far as `min_term`), pulls while the number of running tasks is below the admission
  target, executes with the local `Scraper`, renews at `renew_after`, and commits the encoded result. A renewal
  that returns `Cancel` or an error stops that page. On disconnect the running pages are dropped (the gateway
  reassigns them when their leases expire) and the worker tries the next gateway in the list.
  - Idle wait (empty pull, or every gateway unreachable): binary exponential backoff (Metcalfe & Boggs 1976).
    Floor: upper confidence bound of `q(1−δ)` of the worker's measured pull round trips, or the largest seen
    while there are too few samples. Ceiling: `δ · T`, with `T` the upper confidence bound of `q(1−δ)` of the
    worker's task run times (Conover 1999 §3.2, `pagesift_stat::hazard::quantile_bounds`); before that bound
    exists `T` is the fetcher's total timeout. A pulled task resets the wait to the floor.
  - Politeness hand-off (`SiteStates`): the worker records the hosts it has fetched per site key. On export it
    sends each host's remaining backoff cooldown (`Backoff::check`), `wait` = the largest of them; on import
    the new owner records each as a protocol-given wait (`Backoff::on_throttled(host, Some(wait))`). The rate
    limiter's next-send time and per-host concurrency are not exported (no such interface in
    `pagesift-policy`); for them the gateway's default pause (old owner's leases expire + one RTT bound)
    applies.
- **standby**: opens a follower ledger on its own store, follows the primary (`Standby::follow`). When the
  connection ends it waits until `Standby::deadline()` and reconnects; if the primary is still unreachable and
  `primary_lost()` holds, it calls `take_over()` and then serves as a gateway (HTTP API + worker listener) on the
  same ledger.
- **statistics** (`crates/pagesift/src/cluster/stats.rs`): the render planner's path-family table (Beta counts
  for "render / switch engine gave a gain", `engine/planner.rs`) is aggregated. Workers send `StatsDelta`
  (kind 1, `StatTable<BetaCounts>` keyed by `Scope::Family`): the first observation of a family the gateway has no
  data for is sent at once (it turns the gateway's decision for that family from the cold-start rule into a
  posterior decision); after that, pending observations are sent when they move the posterior mean by more than
  `z(1−δ)·SE` (`pagesift_stat::shrink::significant`). The gateway merges them in the ledger's `StatsHub`
  (order-independent, duplicates dropped by sequence number), journals them, and they reach the standby with the
  journal. Before a worker executes the first page of a path family it asks the gateway for that family's priors
  (`RemoteCoordinator::refresh_priors`, `Scope::Family`) for the render families and each engine's fallback family,
  and imports them where it has no local observations. The browser-engine start table (`learn.rs`, per site
  and engine: "this engine's result was sufficient") goes the same way as kind 2, keyed by `Scope::Site`
  (BLAKE3 of the host, the same on every worker) with metric `1 + engine index`; a worker asks for a site's
  priors before its first page on that site.
- **robots**: the gateway decides the robots mode (request type, `ignoreRobotsTxt`, `allow_crawl_ignore_robots`)
  and puts it in the task; the worker passes it to `scrape_audited` and does not consult its own robots setting.
- **audit**: while executing a task the worker collects the audit records it writes (`audit::COLLECT`; a worker
  without `[audit]` uses `Audit::collect_only`) and returns them with the result; the gateway appends them to its
  audit log with a `worker` field. HTML snapshots stay on the worker (when it has an audit log configured).
- **metrics**: the gateway's `/metrics` appends `pagesift_cluster_worker_pages_total{worker}`,
  `pagesift_cluster_worker_errors_total{worker}` (results the gateway received from each worker) and
  `pagesift_cluster_worker_capacity{worker}` (latest reported admission). The result envelope carries the worker id.
- **job records on the standby**: on a gateway with a journal and persisted jobs, every write to the job store
  (job metadata, page/error/frontier lists with their sequence numbers, the done set, deletions) is also appended
  to the ledger journal as an `App` record (`pagesift_api::JobMirror`, `Ledger::append_app`) and shipped with the
  journal; the standby writes them into its own store (`pagesift_api::apply_op`; list pushes are de-duplicated by
  sequence number). Ledger snapshots include the full job records (`SnapApp`). After takeover the standby builds
  the HTTP service on that store, so `/v2/crawl/{id}` answers and unfinished jobs resume from their last
  completed page. The webhook outbox (`job/{id}/hook`, its sequence and acknowledgement keys) goes through the
  same mirror; on the standby, events at or below the acknowledged sequence are skipped when delivery resumes.
