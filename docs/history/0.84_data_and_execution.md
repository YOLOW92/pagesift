# 0.84 — Data plane and execution plane

Refactoring milestone: the output must stay byte-identical to the frozen 0.81.5 binary.

## What changed

| Area | Before (0.81.5) | Now |
|---|---|---|
| CPU work | semaphore `CPU_SLOTS` + `tokio::spawn_blocking` (unpinned, threads started on demand) | `pagesift_flow::Pool`: one resident worker per core, grouped by NUMA node and restricted to its node's CPU set (unpinned on single-node machines); per-worker queue, idle workers steal from the tail of a queue in the same node first and cross nodes only when the node is empty; each worker parks on its own, no pool-wide lock |
| Async runtime threads | one thread pinned to one logical CPU | one thread restricted to the CPU set of its NUMA node |
| Decompression | on the async thread | on the async thread unless the expected time (bytes × measured time per byte) exceeds a measured cross-thread round trip, then on a CPU worker |
| DOM builds per HTTP page | decode, extract, and the "worth rendering" checks each scanned or parsed the page | one DOM per page: extraction and the client-code check read the same tree (`process_with_workspace_then`) |
| Cache lookup / write | JSON encode and decode on the async thread | on a CPU worker; the document is moved in and back, not cloned |
| Browser early-stop probe | synchronous extraction on the async thread | asynchronous, runs on a CPU worker |
| Network stage gates | could wait | telemetry only |
| Audit log | written under a `std::Mutex` on the request path | a dedicated writer thread (channel + rotation) |

`includeTags`/`excludeTags` and pages whose main content sits in `<noscript>` still parse a second time: their result is
defined as the rewritten document. This happens only when a request asks for tag filters or the page needs it.

Two choices and the measurements behind them:

- Workers are not pinned one per CPU. With async threads and CPU workers both pinned one per CPU, the pair on each
  CPU competed and could not move; on the 16-core test machine throughput at 16 concurrent requests fell from 747 to
  369 pages/s. On the 192-vCPU machine used for 0.70, pinning each thread to one logical CPU cost 33.9 % and
  restricting threads to their NUMA node's CPU set gained 8.63 % (`0.70_p2_step2_numa_executor.md`); cross-node work
  stealing handled 0.163 % of tasks there (`0.70_p2_step4_3_numa_dispatch.md`).
- The pool does not call `malloc_trim` when it goes idle: at one request at a time the pool is idle after every
  request, and trimming returned pages that the next request faulted back in (median latency +8 %).

Estimates used by the execution plane (dispatch latency, decompression time per byte) are means over windows that
close once the relative standard error is below δ (`pagesift_stat::window`), not running means.

## Admin switches

Three crawl-policy switches, on by default, settable only in the config file (`[policy] politeness / backoff / robots`)
or on the CLI (`--no-politeness`, `--no-backoff`, `--no-robots`); the HTTP API cannot change them.

| Switch | Off means |
|---|---|
| `politeness` | no per-site interval, no per-host concurrency cap, robots `Crawl-delay` ignored |
| `backoff` | no 429 / `Retry-After` cooldown, no learned penalty interval, crawl retries without waiting |
| `robots` | robots.txt ignored for every request |

## Byte-identical output

`benchmarks/history/0.84/compare.sh` starts `pagesift serve` for both binaries (cache off, no interval, browser
pointed at an unreachable address) against a local site serving the 1,834 pages of the 0.83 corpus (AEB, WCXB test,
WebMainBench 545, Firecrawl inputs); one page in three is gzip, one in three deflate. Requests: every page with
`engine: http` and formats markdown, html, rawHtml, links, images; every tenth page again with
`includeTags`/`excludeTags` and again with `engine: auto`; one RSS feed and one JSON document. Timing fields and
timestamps are removed before hashing.

| Run | Requests | Different SHA-256 |
|---|---|---|
| `results/20261102-173345` | 2,204 | 0 |
| `results/20261103-073634` (with the changes of 0.85–0.88 in the same tree) | 2,204 | 0 |
| `results/20261103-114343` (0.90 release tree) | 2,204 | 54, all from the main-content changes in `0.88_content.md`: 26 replace the title line with the matching `<h1>`, 27 add headings that were removed before, 1 adds a heading to `html` only; no body paragraph differs |

Cache round trip (`cache_roundtrip.sh`, `results/cache-20261103-073909`, repeated on the 0.90 release tree in `results/cache-20261103-114411` with the same result): the same requests twice with the cache
on; the second pass hit the cache for 2,192 requests (the other 12 are barrier pages, which are not cached), and all
2,204 responses equal the first pass apart from `cacheState` and `cachedAt`.

12 requests in each binary end in `ACCESS_BARRIER` (corpus pages that are challenge or login pages); both binaries
report the same detector and confidence.
