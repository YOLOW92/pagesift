# PageSift 0.70 P2 Step 4.1：NUMA 混合 Reactor 调度

> 日期：2026-10-25  
> 环境：Google Cloud `c4-highcpu-192`，Intel Xeon Platinum 8581C，192 vCPU / 96 物理核 / 2 Socket / 4 NUMA  
> 判定：Step 4.1 通过。同一构建、同一时间窗口的固定三轮 A/B 中，混合调度中位吞吐提高 `9.14%`，三轮均为 `failed=0`。

## 问题

第四步的旧路径使用 192 个 Reactor，每个 Reactor 同步完成 socket 状态机和正文解析。连接等待时，同一线程的解析能力也被挂起；反过来，解析变慢时 Reactor 不能及时继续推进其他连接。96 Reactor 固定对照仅得到 `773,569 pages/s`，证明简单减少 Reactor 线程不是答案。

首版“48 Reactor + 144 内容 Worker”把两阶段完全拆开，但完成队列满时让 Reactor 等待，正式三轮中位约 `895,912 pages/s`，没有形成可靠吞吐优势。该阻塞策略被否决，没有作为默认候选。

## 实现

- Reactor 数由拓扑和连接深度计算：按每个 Reactor 约 32 个连接估算、上限为一半物理核，并向 NUMA 节点数对齐；192 vCPU / 1,536 连接自动得到 48 Reactor，不编码 P1 的某个甜点核心数。
- 四个 NUMA 节点各拥有 12 个 Reactor、36 个内容 Worker和 384 条固定连接。
- 每个 Reactor 拥有独立有界完成队列和响应缓冲回收池；三个内容 Worker 只消费该 Reactor 的任务，所有线程 affinity 均限制在同一 NUMA 节点。
- Socket、连接状态机和任务序号始终由原 Reactor 所有；只移动已完成的响应缓冲，不移动连接。
- 固定 fixture 的 `Options/Url` 在各 Reactor/内容 Worker 完成 affinity 后建立本地副本，避免每页克隆，也避免所有节点反复读取主线程首次分配的 URL backing storage。
- 队列有容量时把正文交给本地内容 Worker；队列已满时，Reactor 立即在本线程解析当前页并继续连接。该决策来自当前队列状态，不依赖手工阈值或参数扫描。
- 队列、回收池、inline 回退和节点计数全部使用 Safe Rust；Crossbeam 仅作为有界通道原语，调度、所有权、背压与回退算法由 PageSift 实现。

## 固定 A/B

共同条件：同一 release 构建、12 路 `SO_REUSEPORT` 本机源站、1,536 连接、5 个固定页面、每轮 10,000,000 页。CPU 只统计 Runner 自身 `/proc/self/stat` 的 `utime + stime`，不把源站或系统 CPU 计入 Runner。

| 路径 | 三轮 pages/s | 中位 pages/s | CPU 时间中位 | 平均占用核心中位 | 单核产出中位 | RSS 最大值 | failed |
|---|---|---:|---:|---:|---:|---:|---:|
| 192 Reactor 同步网络+解析 | 822,980 / 823,456 / 833,406 | 823,456 | 1,314.74 core-s | 108.89 | 7,606 pages/core-s | 252.88 MiB | 0 / 0 / 0 |
| 48 Reactor + 144 Worker 混合回退 | 899,951 / 898,706 / 898,752 | **898,752** | 1,354.80 core-s | **121.93** | 7,381 pages/core-s | **247.33 MiB** | 0 / 0 / 0 |

混合调度的中位吞吐提高 `9.14%`，Runner CPU 时间增加 `3.05%`，平均活跃核心增加约 `11.98%`，峰值 RSS 下降约 `2.19%`。单位 CPU 产出下降 `2.96%`，这是用更多原本等待的 CPU 换取更高总吞吐的明确取舍。

混合候选的中位 queue-backpressure 事件为 33,526，仅占一千万请求的约 `0.34%`；这些事件触发 Reactor 本地解析，而不是等待。三轮全部满足：

- `completed = valid = 10,000,000`；
- `failed = retries = timeouts = 0`；
- `connects = 1,536`、`reused = 9,998,464`；
- Runner `process_cpu_time_s` 有效；
- 峰值 RSS 低于第四步的 500 MiB 门槛。

## 结论边界

本次结论只使用同一时间窗口内的配对 A/B。历史第四步中位数为 `916,514 pages/s`，高于本轮混合候选的绝对值；由于同机动态源站与 Runner 争用同一批 CPU，不能把跨时间窗口差异归因于调度器。Step 4.1 证明的是在当前相同外部条件下，分层混合调度能显著提高 Runner 吞吐并激活更多核心，而不是宣称已经突破所有历史峰值。
