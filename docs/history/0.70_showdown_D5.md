# 0.70 十域对决 · D5 RAG 分块与 BM25 检索

## 口径

| 项 | 值 |
| :--- | :--- |
| 数据 | ChunkEval：5 个语料（chatlogs / finance / pubmed / state_of_the_union / wikitexts，共 1.45 MB）+ **472 个问题**，每题带答案在原文中的字符区间 |
| 指标 | **Recall@5**：用 BM25 检索 top-5 块，若某块完整覆盖答案区间（或覆盖 ≥80%）即算命中 |
| 内存 | 每个参赛者 10 GiB 上限 |
| 分块目标 | 约 512 token/块（PageSift 的 fixed/sliding/overlapping/recursive；竞品按各自等价参数） |

## 关键说明：`whole` 与 `headings` 的 1.0000 不计入排名

这两行的块数都是 **472**，与问题数完全相同 —— 说明每篇语料实际只切出 1 个块，
整篇内容原样送进 BM25，答案必然在块内，**Recall 恒为 1.0**。

- `whole` 是故意的对照组（不切块）。
- `headings` 之所以退化成整篇，是因为这 5 个语料**几乎没有 Markdown 标题**，
  `Headings` 策略找不到切分点，只能输出整篇。

因此这两行只作参考，不参与「分块质量」排名。

## 真正的对比：PageSift fixed 0.9470 是最佳可用分块方案

在**块大小合理（约 512 token）**的方案里：

| 方案 | Recall@5 | 相对 semchunk |
| :--- | ---: | ---: |
| **PageSift fixed** | **0.9470** | **+0.0106** |
| PageSift overlapping | 0.9428 | +0.0064 |
| PageSift sliding | 0.9407 | +0.0043 |
| semchunk（Python 生态主流） | 0.9364 | 基准 |
| PageSift recursive | 0.9004 | −0.0360 |
| chonkie | 0.7203 | −0.2161 |
| langchain | 0.4703 | −0.4661 |

**PageSift 三种窗口策略（fixed / overlapping / sliding）都超过 semchunk**，
其中 fixed 领先 1.06 个百分点。速度上 fixed 与 semchunk 量级相当（1.89 s 对未计时）。

## 按语料的 Recall@5（PageSift fixed）

| 语料 | Recall@5 | 问题数 |
| :--- | ---: | ---: |
| chatlogs | **1.0000** | 56 |
| wikitexts | 0.9861 | 144 |
| state_of_the_union | 0.9474 | 76 |
| finance | 0.9072 | 97 |
| pubmed | 0.8990 | 99 |

pubmed（医学文献，术语密集、句长差异大）最难，chatlogs（对话，边界清晰）最易。

## 意外发现：`recursive` 反而不如 `fixed`

PageSift 自己的 `recursive` 策略只得 0.9004，比 `fixed` 低 0.047。
原因是 `recursive` 会尊重段落与句子边界，切出的块偏小（377 token vs 509），
在 BM25 这种按词频打分的检索下，块越小命中完整答案的概率越低。

**这与「recursive 是 RAG 推荐策略」的直觉相反。** 对本数据集，固定窗口更有效。
建议在文档中注明：分块策略应按下游检索器选择，recursive 更适合嵌入向量检索
（语义完整优先），fixed/overlapping 更适合 BM25（信息密度优先）。

## 与 0.50 的关系

0.50 报告的 D5 指标是 R@1000 = 0.895、BM25 QueryFilter 1.35 ms/q，
与本次 Recall@5 不是同一口径，**不可直接比较**。本次为同机同数据重新建立基线。
