# 0.88 — RAG 分块：按块结构合并

**背景。** 0.81 的 `recursive` 分块（`{"type":"recursive","size":200}`）在 250 词检索预算下的召回是 0.607，
低于 LangChain recursive 的 0.626。本次在块预算 100 / 200 / 400 × 检索预算 250 / 500 / 1000 的全部 9 格上，
对召回和 IoU 各做一次配对检验（共 18 个），判定方法见"评测"。

指标方向：召回（R）、IoU 都是越高越好；块数、平均块长只作说明。

**结果。** 全部 18 个检验（9 格 × 召回 / IoU）都没有判为下降；块预算 400 的三格召回显著提升。块预算 200 / 检索 250
的召回 0.607 → 0.633，Δ = +0.026，95% 区间 [−0.006, +0.058]，区间含 0。

## 做法

改动在 `crates/pagesift-extract`：新文件 `src/pack.rs`（片段怎么合并成块），`src/recursive.rs` 改为调用它，
`ChunkStrategy::Recursive` 默认用新的合并方式（`Pack::Structure`）。

切分层级不变（Markdown 块 → 最长换行串（段落）→ 换行 → 句末标点 → 其他标点 → 空白 → 字），变的是同一层里
相邻片段怎么合并成块。0.81 是 semchunk 的贪心：往一块里塞到下一片放不下为止，块长贴着预算（块预算 200 时
平均 138 词），250 词的检索预算往往只放得下一块；切超长段落时最后还常剩一小截。

新规则：

1. 不超过块预算的单个片段（一整段、一整个列表、一整张表、一整段代码）整块保留，不切开；
2. **整块之间**（Markdown 块、段落、行）切开不会切断内容，合并得小一些：块长不超过
   `max(块预算/2, 这一串里最长的块)`。块预算的一半保证一个预算里至少放得下两块合并出来的块；最长块说明
   这一串的自然块本来就有这么长，小块合到同样长度不算稀释；
3. **超长块内部**（句子、子句、词）每切一刀都可能切断一句话，所以切得最少：上限就是块预算；
4. 在上限下取最少块数，再在同样块数里取最小的最大块长（线性划分，min-max），块长均衡、不留零头；
5. 标题不放在一块的结尾（沿用 0.81）。

块长由块预算和这一串片段的长度分布决定，没有另外的块长或重叠参数。合并上限只用到"块预算的一半"这一个
推导出的系数（代码里标 `[推导]`），而且只用在整块之间。

queryFilter（`filter_markdown_by_query`）的打分单位也用 `Recursive{size:100}` 切分，它的阈值是按旧的合并方式
评测出来的，所以继续用旧的贪心（`Pack::Greedy`），输出与 0.81 逐字一致（见下）。

### 选择与理由

- 分块边界取自 `pagesift-extract` 里已有的 `chunk::markdown_ast::Doc`（带字节区间的标题、段落、表格、代码块）
  加纯文本的换行层级，没有复用 `pagesift-plan` 的 `block::split`：后者不保留字节位置（按行拼接成新字符串，
  并为每块算 BLAKE3 指纹），而分块需要原文区间。列表在 `Doc` 里归为段落，
  空行分隔的列表是独立块；不超过块预算时同样整块保留。
- "块长由块预算和块长度分布决定"只用在整块之间；超长块内部改用"切得最少"，理由见下面"没有采用的方案"。

## 评测

| 数据 | Chroma chunking_evaluation：5 份语料（chatlogs、finance、pubmed、state_of_the_union、wikitexts），472 题 |

### 其他输出

- `fixed_tokens`、`sliding_window`、`paragraphs`、`sentences` 四种策略的输出与基线逐字节相同。
- queryFilter：`qf_ranks` 输出里实际返回给用户的 `pagesift-default` 和 `pagesift-old-default` 与基线逐字节相同；
  `rag.sh` 的 `rag.qf.*` 指标只取 `pagesift-default`，因此不变。`qf_ranks` 里用公开 `Recursive` 策略做的分析行
  （`pagesift-rec*`、`rec100-*`）随分块变化，它们不是产品输出。
- 分块耗时只记在 `time.txt` 里备查，没有做测速，不作结论。

## 没有采用的方案

| 方案 | 块预算 200 / 检索 250 召回 Δ | 问题 |
|---|---|---|
| 第一版：整块之间和超长块内部都按 `max(块预算/2, 最长片段)` 合并 | +0.063 [+0.027, +0.099]，提升 | 有回退：块预算 100 时 R@1000 −0.033 [−0.053, −0.012]，IoU@250 / 500 / 1000 下降；块预算 200 时 IoU@1000 −0.002 下降 |
| 给 `recursive` 加"检索预算"参数，按它定合并上限 | — | 要改公开接口；评测里只有块预算 200 / 检索 250 这一格受益 |
| 只做均衡，上限 = 块预算 | −0.010 | 块数和平均块长都不变，没有提升；块预算 100 时 IoU@250 下降 |
| 超长块内部切成"文档里整块的长度尺度"（至少块预算一半） | +0.058，提升（调参半） | 块预算 100 时 IoU@250、IoU@1000 下降 |
| 整块之间只合并到最长块那么长，超长块内部按块预算均衡 | +0.016 | 提升更小 |

冲突的来源：块预算 200 时，250 词检索的提升几乎全来自把超长段落切到约 100 词（finance、chatlogs、pubmed）；
块预算 100 时同样切到块预算的一半只剩约 50 词，1000 词的召回和 IoU 就下降。两边要的都是约 100 词，也就是
250 词检索预算的一半，而分块器不知道检索预算。只按块预算比例定上限的规则，在块预算 200 下提升 250 词召回，就会在块预算 100 下让 1000 词的召回或 IoU 下降。

## 限制

- 块预算 200 / 检索 250 的召回 Δ = +0.026，95% 区间含 0（点估计 0.633，高于 LangChain recursive 的 0.626）。
- 评测语料都是纯文本（没有 Markdown 标题、列表、表格、代码块），Markdown 块结构的那部分只由模块测试覆盖。
