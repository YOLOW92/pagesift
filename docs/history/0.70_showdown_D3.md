| 项 | 值 |
| :--- | :--- |
| 机器 | Intel i7-10700，8 物理核 / 16 逻辑核，15 GB，Ubuntu 26.04 |
| 数据 | `allenai/olmOCR-bench` 官方全量 **1,403 PDF / 7,019 项检查**（bench_data 完整 7 个 jsonl） |
| 指标 | 官方 `olmocr/bench/tests.py` 逐项判定，通过率 = 通过项 / 全部项 |

| 数学项 | 用 KaTeX + Chromium 真实渲染比对（官方口径），3,385 个唯一公式已预热缓存 |

## 关键结论

1. **0.70 与 0.50 在 D3 上完全相同**（0.4506）。本轮没有改 PDF 处理路径，符合预期。
   这反过来也验证了 0.70 的改动（正文定位策略）没有误伤 PDF 提取。
2. **PageSift 是唯一一个在所有 6 类测试上都明显领先的实现**，尤其在 `order`（0.5523）
   与 `table`（0.5814）这类结构性项上，纯文本抽取器（pypdf/pdfminer）几乎拿不到分。
3. **`math` 项 0.3530 是主要失分点**（3,385 项，占全部检查的 48%）。
   失分原因是公式需要 LaTeX 精确还原，而我们的 PDF 层做的是版面重建而非公式识别。
4. **扫描件（old_scans / old_scans_math）接近零分**，因为 PageSift 不含 OCR，
   纯图像页没有文本层可抽。这是能力边界。

## 与 0.50 报告的差异说明

0.50 的 D3 报告声称「olmOCR-bench 官方全量」，实际只跑了 **1,269 篇**，
且通过率报的是 **71.0%**。本次用官方 1,403 篇 + 官方评分器全量测得 **45.06%**。

差异原因：0.50 用的是相对宽松的自制判定（按子集人工比对），
本次用的是官方 `tests.py` 的逐项单元测试（含 `present`/`absent` 的精确字符串匹配、
`math` 的 KaTeX 渲染像素比对、`table` 的 HTML 结构树比对）。**两者不可直接比较**，
以本次为准。
