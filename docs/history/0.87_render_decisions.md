# 0.87 — Render decisions, candidate merge, embedded JSON

## What changed

| Decision | Before (0.81.5) | Now |
|---|---|---|
| Open a browser for an `engine: auto` page | HTTP text below 1200 weighted characters (300 for articles), page ≥ 4096 bytes or has scripts; per-site "render gain" counter (3 misses in a row → skip, explore every 16th) | The same rule is the candidate gate. Inside the gate, per path family (origin + first path segment + whether the page has client-side code) a Beta count of "rendering helped" (see the next row) decides by Thompson sampling: render ⇔ `p·(1 − Q_http) > E[render seconds]·(λ_browser + 1/remaining deadline)`. A family with no observations follows the 0.81 rule. Counts are sharded by family hash and saved to the store (`plan/render`, versioned). |
| Keep the rendered result | rendered text ≥ HTTP text + 200 characters | three candidates (HTTP, rendered, block merge of both). The rendered or merged result is kept when it has more weighted text than the HTTP result (the 0.81 rule) or when its calibrated quality score is higher; the merged result replaces the rendered one when it adds blocks only HTTP had and scores at least as high. The quality score alone never discards a rendered result that 0.81 would keep: it does not reward length, and a page whose HTTP text is a title and a one-line description can score close to 1. The same rule is the "gain" the render decision learns from. |
| Text in page data islands (`__NEXT_DATA__`, `__NUXT_DATA__`, `application/ld+json`) | not used | when the HTTP text is short enough to consider rendering, string leaves longer than the page's own `q(1−δ)` leaf length that look like prose are turned into blocks and merged with the HTTP blocks; the merge is used only for the HTTP result that is returned when no browser result is kept, and only when it adds blocks and raises the quality score. The render decision and its learning use the HTTP result without it. |
| Try the next browser engine after a non-iframe-rendering engine | rendered text below 200 characters | the same rule is the candidate gate; inside it, per path family and engine position a Beta count of "the next engine helped" (more weighted text, or a higher quality score) decides with the same rule as rendering, and every fallback records the outcome |
| Which browser engine to start with, per site | 3 fallbacks in a row → start at the fallback engine; every 16th request explores from the first | per site and engine a Beta count of "this engine's result was sufficient", Thompson-sampled along the engine chain; prior 3 "sufficient" pseudo-observations and none "insufficient" (a site never seen failing always starts at the first engine; after 3 failures the posterior mean is 1/2); counts decay by `1−δ` per observation so a site that changes is relearned |
| Learner table | 100 000 sites, cleared when full | same capacity, sharded by host hash (at least `1/δ` sites per shard); a full shard drops the half with the least evidence |
| Start the browser while the HTTP body is still being extracted | never | when the HTTP body has arrived: start ⇔ `p·s > (1−p)·(s+c)/(1−ρ)`, with `p` the family's posterior mean of "rendering helped" (family split by whether the first 4096 bytes contain `<script`), `s` the expected extraction time (extraction seconds per HTML byte, windowed ratio × body size), `c` the lower `q(δ)` bound of the first engine's time to document, `ρ` the browser-tab utilization of the admission facade. No family observations or no extraction estimate yet → never. A started render runs as if the HTTP text were empty (no navigation cap, no early stop) until extraction gives the probe its baseline; it is cancelled when the render gate then says no, and its result goes through the same adopt/merge step. |
| Result after falling back from a non-iframe engine to a full engine | the full engine's result | blocks only the first engine had are merged into the full engine's result; the merge is used when its quality score is not lower than the full engine's result (no quality score → no merge) |
| glibc `M_ARENA_MAX` | 4 | `max(4, ⌈CPUs/4⌉)`: 4 was validated on 16 logical CPUs; larger machines keep the same number of CPUs per arena (192 vCPUs → 48) |

## Explanation output

`"explain": true` in scrape options (CLI: `pagesift scrape --explain`) writes the decisions to
`metadata.pagesift.plan.steps`, one entry per step:

| `action` | `chosen` | Fields |
|---|---|---|
| `embedded-json` | data-island text was merged in | `blocks` = [in both, HTTP only, data island only], `quality`, `value` (quality gain) |
| `speculate` | a browser was started before extraction | `learned` (false = cold start, not started), `p` (posterior mean), `value` (`p·s` seconds), `charge` (seconds) |
| `render` | a browser was opened | `learned` (false = 0.81 rule), `p` (sampled probability), `value` (`1 − Q_http`), `charge`, `quality` (`Q_http`) |
| `adopt` / `merge` | the rendered (`adopt`) or merged (`merge`) result was used | `blocks`, `value` (quality difference), `quality` |

Requests with `explain` bypass the cache, so the steps describe the current fetch.

## Tests

- `crates/pagesift-engine/src/engine/planner.rs` and `pagesift-plan` tests: cold start equals the 0.81 rule, the
  learned decision follows the posterior, the merged result is used only when it adds HTTP-only blocks and does not
  score lower, data-island text is merged only into the returned HTTP result.
- `crates/pagesift/tests/it`: `explain` writes one step per decision; requests with `explain` bypass the cache.
- With `engine: http` the local comparison set is unchanged by these decisions (`0.84_data_and_execution.md`).
