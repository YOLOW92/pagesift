# PageSift 0.70 P2：全自研 Rust NUMA 数据面五步计划

> 日期：2026-10-25  
> 目标：替换 0.61 遗留的通用 Tokio/reqwest 热路径，在保留 CPU、并发、分片自适应的前提下，构建 NUMA-Local、固定所有权、无逐页 Spawn 的 Rust 请求执行微内核。  
> 当前有效基线：Intel Xeon 192 vCPU，100M，`634,229.97 pages/s`，0 失败；自动选择 180 活跃 vCPU、1536 并发、72 分片。

## 不可破坏的原则

1. 最终运行不接受手工指定核心、并发或分片甜点；所有容量由控制器在线确定。
2. 正式 CPU 指标只使用受测 Runner 自身 `/proc/self/stat` 的 `utime + stime`；系统 CPU 和源站 CPU 只能作为诊断旁证。
3. `failed > 0` 的配置只能记录为不稳定点，不能成为正式最优候选。
4. 每一步只替换一个主要变量，保留可重复 A/B 对照；未达到验收条件不得进入下一步结论。
5. “全自研”指 PageSift 自研调度器、Reactor、HTTP 状态机、连接池、缓冲池和控制器；TLS 密码算法继续使用审计过的 Rustls，不自行实现密码学。

## 第一步：组件归因与公平基线

> 本机归因已通过，结果见 [`0.70_p2_step1_component_attribution.md`](0.70_p2_step1_component_attribution.md)；远端独立源站复核待最终验收前补齐。

### 目标

先把网络等待、任务调度、响应聚合、HTML 建树、正文抽取和 Markdown 渲染的成本分开，确认每个阶段消耗了多少进程 CPU 时间和墙钟时间，避免继续凭总 QPS 猜瓶颈。

### 实施

- 为 Runner 增加分阶段遥测：`dispatch`、`socket_wait`、`body_read`、`html_parse`、`extract`、`markdown`、`drop/recycle`。
- 建立三条固定对照路径：预生成负载的纯解析、只收响应不解析的纯传输、完整端到端。
- 固定页面集、页面大小、页面模态和随机种子；源站与 Runner 拆分 CPU/NUMA 集合，另做远端源站复核。
- 输出每阶段调用数、总耗时、均值、P95/P99、进程 CPU 时间和跨 NUMA 诊断数据。

### 验收门槛

- 三条对照均可重复执行，连续三次结果离散度不超过 3%。
- 分阶段计时可解释至少 95% 的 Runner 墙钟路径。
- 明确列出前三个成本中心；没有归因报告，不开始大规模重写。

## 第二步：自研 NUMA-Local 执行器

> 状态：已通过。相同 HTTP/内容组件的四轮 A/B 中位数由 `656,052.09` 提升至 `712,643.07 pages/s`（`+8.63%`），正式候选全部零失败。关键结论是使用 NUMA 节点级 affinity、允许节点内调度；逐逻辑 CPU 精确绑核在双路 Intel SMT 上会稳定退化。详见 [`0.70_p2_step2_numa_executor.md`](0.70_p2_step2_numa_executor.md)。

### 目标

从热路径移除全局 Tokio 工作窃取和逐页 `tokio::spawn`，让请求从创建到回收始终归属于同一 NUMA 域。

### 实施

- 每个 NUMA 节点建立独立 Reactor、固定 Worker 组和本地任务槽池。
- Worker affinity 限制在所属 NUMA CPU 集内，物理核作为初始容量层、SMT 作为自适应扩展层；禁止逐逻辑 CPU 精确硬绑，让内核保留节点内避让能力。
- 以固定容量 Slot 状态机批量推进任务，不为每个页面创建 Future/Task。
- 节点内使用有界环形队列；跨节点禁止工作窃取，只允许全局控制器重新分配新任务预算。
- 保留现有 HTTP 协议实现作为临时变量，单独验证执行器收益。

### 验收门槛

- 输出与现有 Runner 字节级/语义级一致，0 丢任务、0 重复任务。
- 192 vCPU 下各 NUMA 节点有独立进度和 CPU 遥测，不再出现任务长期集中单节点。
- 相同传输和解析组件下，吞吐明确高于全局 Tokio 对照；否则停止并解释未改善原因。

## 第三步：自研分片 HTTP Reactor 与连接池

> 状态：已于 2026-10-25 按用户确认的验收边界完成。10M 纯传输中位数 `835,567.18 req/s`，较 reqwest 对照提升 `15.87%`；10M 完整链路中位数 `913,012.49 pages/s`，提升 `28.10%`，全部零失败；另完成 10,000 个真实 HTTPS 域名的生产 Rustls 基线。Mio Reactor 原生 Rustls 接入保留为后续优化，不阻塞第四步。详见 [`0.70_p2_step3_http_reactor.md`](0.70_p2_step3_http_reactor.md)。

### 目标

从正式直连热路径移除 reqwest/hyper 的通用请求生命周期，建立与 NUMA Worker 同所有权的 HTTP 数据面。

### 实施

- 使用 Linux `epoll` 或经实测选择的 `io_uring` 建立批量事件循环，不在完成事件上生成新任务。
- 自研 HTTP/1.1 请求编码、增量响应头解析、Content-Length/Chunked 状态机和连接复用。
- 每个 NUMA 节点拥有独立连接池、空闲队列、超时轮和失败重试状态；不使用全局 `Mutex<HashMap>`。
- 连接、Socket、缓冲区和解析 Worker 固定同节点；支持多地址、多端口和 `SO_REUSEPORT` 队列映射。
- TLS 只保留 Rustls 密码学边界，PageSift 自主管理握手状态、连接归属和调度。

### 验收门槛

- HTTP/1.1 keep-alive、chunked、断连、超时、幂等重试和限长测试全部通过。
- 纯传输对照中不再出现每页 Spawn、完整响应二次聚合或全局连接池锁。
- 本机多队列与远端源站两类测试均优于旧 reqwest/hyper 路径，且失败为 0。

## 第四步：NUMA 本地内存与融合解析流水线

> 状态：已于 2026-10-25 完成。Worker 本地 DOM/正文索引容量复用使内容纯 CPU 中位吞吐提升 `10.29%`；完整 Reactor 中位吞吐小幅提升 `0.38%`、CPU 时间下降 `1.65%`，峰值 RSS `244.72 MiB`，正式候选零失败。详见 [`0.70_p2_step4_numa_memory_pipeline.md`](0.70_p2_step4_numa_memory_pipeline.md)。

### 目标

消除 URL、响应体、DOM 和 Markdown 在不同线程/NUMA 节点间分配与释放造成的远端内存访问，并减少重复 DOM 遍历。

### 实施

- 每个 Worker 建立可复用 Arena/Slab：请求槽、URL 路径、响应块、DOM 节点和输出缓冲按页整体复位。
- 响应数据直接进入本地块链或连续缓冲，解析完成前不跨节点转移所有权。
- 缓存源站基址和 URL 结构，只编码变化的页面 ID，去除每页 `format!` 与完整 `Url::parse`。
- 合并 metadata、正文候选、可见字符和 Markdown 所需的可共享遍历结果。
- 为 HTML、正文抽取和 Markdown 分别保留正确性基准，性能优化不得降低质量评分。

### 验收门槛

- 热路径分配次数和跨线程释放次数有明确下降，并提供前后数据。
- 峰值 RSS 不高于当前 100M 基线的 500 MiB 安全线。
- 固定语料的 Markdown、metadata、链接及正文质量测试全部通过。

## 第四步后续：数据面剩余瓶颈拆解

第四步把内容阶段的纯 CPU 中位吞吐提高了 `10.29%`，但完整链路仅提高 `0.38%`，同时 Runner 平均只使用约 `132/192` 个逻辑 CPU。这不是性能上限，而是说明瓶颈已经从内容内存分配迁移到网络数据面的供给与分发。后续固定拆为以下五项，逐项提供可复算证据：

### 4.x 共同自适应验收约束

- 4.1 至 4.5 的每一项都必须接入运行期闭环，而不是只给出某台机器的静态甜点；人工参数只允许表达安全上限与冻结 A/B 基线。
- 启动时根据有效 CPU、物理核、Socket、NUMA、内存和连接条件自动建立初始配额；运行中依据吞吐、延迟、队列深度、PageSift 进程 CPU、内存、失败和每 host 反馈调节。
- 控制器必须具备有界方向探测、退化回退、最佳点锁定和低频复探；禁止永久扫描、全网格搜索和频繁创建/销毁线程。
- 局部异常只收缩对应 NUMA 域、阶段或 host；快速 host 和健康阶段不得为慢 host 的过载承担全局退避。
- 每项报告必须分别证明自动扩张、自动回退和稳定锁定，并保留固定模式作为可复算对照。

### 4.1 NUMA 分层 Reactor 调度与本地完成队列

> 状态：已于 2026-10-25 完成。固定三轮配对 A/B 中，中位吞吐从 `823,456` 提升到 `898,752 pages/s`（`+9.14%`），平均活跃核心从 `108.89` 增至 `121.93`，候选全部零失败。详见 [`0.70_p2_step4_1_hybrid_reactor.md`](0.70_p2_step4_1_hybrid_reactor.md)。

- 把当前“每个 Reactor 同步执行网络状态机和正文解析”的耦合路径拆开；
- 每个 NUMA 节点分别拥有网络 Reactor、内容 Worker、有界完成队列和响应缓冲回收池；
- Socket 与连接状态始终由原 Reactor 所有，正文任务只在同节点交付，队列满时显式背压；
- 自动按拓扑和连接深度计算网络/内容线程配额，不编码 P1 的某个甜点核心数；
- 在固定拓扑线程集合之上用统一闭环调整活跃内容 Worker 配额和 Reactor 原地解析份额；线程不重建、不迁移 Socket，配额按 NUMA 量子移动；
- 仅执行一次固定旧/新 A/B，不进行线程数或并发网格扫描。

### 4.2 连接生命周期与按主机热连接水位

- 独立管理建连、TLS、连接池查找、复用、重连和超时；
- 按 host 的 RTT、错误率和服务时间动态维持热连接水位，慢主机只收缩自身窗口。
- 429/503 触发 host 本地快速退一级，同一过载窗口不得叠加惩罚；健康饱和窗口逐级扩张，延迟退化、取消和网络失败参与回退。

### 4.3 NUMA 本地任务入口、批量分发与 work stealing

> 状态：已于 2026-10-25 完成。三轮平衡负载中自适应分发的吞吐代价为 `0.68%`，背压中位数下降 `30.63%`；单 NUMA 扰动下吞吐提升 `1.93%`、背压下降 `22.36%`，全部零失败。详见 [`0.70_p2_step4_3_numa_dispatch.md`](0.70_p2_step4_3_numa_dispatch.md)。

- 以节点本地队列和批量领取替换全局入口争用；
- 只在本节点饥饿时跨节点 stealing，并记录跨节点比例和代价。
- 批量大小、本地低/高水位和 stealing 触发阈值必须由闭环根据队列与服务时间自动调整，不写死 Xeon 参数。

### 4.4 DNS/TCP-TLS/HTTP/解析/输出分阶段背压

- 各阶段拥有独立容量、队列深度、服务时间、失败率和长尾遥测；
- 控制器分别调节阶段窗口，禁止一个“总并发”参数掩盖局部阻塞。

### 4.5 四层归因、分阶段公网自适应门禁与 100,000 真实网站验收

- 固定本地源站、纯传输、完整解析和真实公网四类对照；
- 区分可优化的 Reactor/连接/分发成本与不可控的公网 RTT、限速及远端长尾；
- 外部瓶颈必须有分阶段数据证明，不能用低 CPU 或总吞吐直接推断。
- 四层对照用于验证同一控制器能换环境自动收敛，不允许为每层手工换一组并发、分片或线程比例。
- 将单一全局并发拆为 DNS、TCP/TLS 握手、活跃 HTTP、解析和长尾槽五类独立容量，由控制器自动收敛，禁止人工扫网格和永久扫描。
- DNS 支持正负 TTL 缓存、同域 Singleflight、错误码/延迟直方图和仅针对瞬时错误的有限重试；缓存结果在使用时仍必须通过 SSRF 校验。
- TCP/TLS 支持 Happy Eyeballs、握手并发隔离、连接复用和可重试错误分类；证书错误与确定性协议错误不得重试。
- robots 保持 RFC 9309 合规，增加跨批次缓存、条件请求和连接复用；不得以提升成功率为由绕过 `Disallow`。
- DNS、连接、TLS、TTFB、body idle 使用分阶段 deadline；长尾任务进入有界隔离槽且不得阻塞主队列，也不得被伪装成已完成。
- 控制器只让瞬时 DNS/网络/超时和 429 影响相应阶段容量；robots、SSRF、访问屏障和确定性失败不得触发全局降并发。
- 最终使用冻结的 100,000 个真实网站集合复测，输出成功率、有效正文率、各阶段 P50/P95/P99、受测进程 CPU 时间和完整错误分布；未通过不得发布 `0.70.0`。

## 第五步：四维自适应整合与 100M/200M 验收

### 目标

把新数据面交给分层控制器管理，在不同 CPU、Socket、NUMA 和网络条件下自动找到稳定甜点，而不是依靠人工扫网格。

### 实施

- 每个 NUMA 域独立调节本地活跃 Worker、连接深度和任务槽；全局控制器调节域预算、总并发和分片数。
- 自适应维度固定为：CPU/SMT 容量、并发、分片、网络队列/连接深度。
- 采用有限方向探测、回退、锁定和低频挑战；禁止永久扫描。
- 在 1/8/24/48/96/192 vCPU 和 NUMA 边界上做缩放验证；有条件时追加单路 AMD 复核。
- 先跑三次 100M 确认，再按用户指示执行正式 200M。

### 验收门槛

- 不传手工核心、并发、分片和连接深度参数，控制器能自行收敛并锁定。
- 正式候选全部 `failed = 0`，进程 CPU 时间有效，报告可复算。
- 100M 三次确认中位数至少达到 `760,000 pages/s`（当前 634,230 的约 20% 提升）；未达到则 P2 不标记完成，并提交剩余瓶颈证据。
- 192 vCPU 稳态 Runner CPU 目标为 80% 至 90%+；若受外部源站限制，必须由纯传输/纯解析对照证明。
- 200M 仅作为最终稳定性验收，不参与寻找参数。

## 执行顺序与停止规则

严格按 `归因 → 执行器 → HTTP Reactor → 内存/解析 → 自适应验收` 执行。任何一步未达到验收门槛，都停留在该步解决根因，不通过增加扫描次数、写死 Xeon 参数或缩小 CPU 集合掩盖问题。

Step 4.5 同时承担四层性能归因与发布前最终公网分阶段自适应门禁：分别控制 DNS、TCP/TLS、HTTP、解析和长尾槽，并最终用冻结的 100,000 个真实网站集合复测。该门禁未通过，不得进入 `0.70.0` 发布。
