# PageSift 0.70 P2 Step 1：组件归因报告

> 日期：2026-10-25  
> 环境：Google Cloud `c4-highcpu-192`，192 vCPU，96 物理核，2 Socket，4 NUMA  
> 状态：本机固定负载、阶段采样和 NUMA 共置对照完成；远端独立源站复核待补。

## 1. 目的

回答当前约 63.4 万 pages/s 的上限主要来自哪里，并判断第二步应优先替换 HTML/正文处理还是请求执行微内核。

正式 CPU 口径始终为组件探针进程自身 `/proc/self/stat` 的 `utime + stime`。源站和系统级 CPU 只参与拓扑诊断，不计入 Runner CPU。

## 2. 方法

新增 `p2_component_probe`，所有模式使用同一组从正式合成源站预取的五类页面：

- `url_dispatch`：URL 编码与解析。
- `transport_only`：相同 reqwest 客户端、96 个分片池、1536 个长生命周期槽，只读取响应体。
- `html_dom`：只运行自研 `pagesift_html::Html::parse`。
- `content_total`：运行完整 `pagesift_content::process`。
- `end_to_end`：传输、响应聚合、URL 解析、完整内容处理和回收。

网络和端到端模式各运行 1000 万操作三次；CPU-only 模式扩大到 URL 10 亿、DOM 2 亿、完整内容 5000 万操作。另在 2000 万端到端操作中按 1/4096 采样阶段时间。

为分离本机源站污染，固定 Runner 使用 NUMA 1/2/3 的 144 vCPU，源站固定使用 48 vCPU，分别测试：

- `isolated`：源站位于 NUMA 0，与 Runner 完全隔离。
- `shared`：源站位于 NUMA 1，与 Runner 共置，但源站与 Runner 的 CPU 数、Runner 并发和分片数保持不变。

## 3. 三次重复结果

| 路径 | 三次吞吐 | 中位数 | 相对中位数最大偏差 | Runner 核心用量中位数 | 失败 |
|---|---:|---:|---:|---:|---:|
| URL/调度 | 164.79M / 165.04M / 157.25M | 164.79M ops/s | 4.58% | 190.17 | 0 |
| 纯传输 | 715,976 / 711,432 / 720,597 | **715,976 req/s** | **0.65%** | 43.22 | 0 |
| 纯 DOM | 29.72M / 30.04M / 30.12M | **30.04M pages/s** | **1.07%** | 188.52 | 0 |
| 完整内容 | 1.888M / 1.987M / 1.934M | **1.934M pages/s** | **2.69%** | 185.90 | 0 |
| 端到端 | 663,949 / 661,999 / 665,881 | **663,949 pages/s** | **0.29%** | 130.19 | 0 |

三条决定主结论的路径——纯传输、完整内容、端到端——均满足三次结果相对中位数偏差不超过 3%。URL 微基准第三次偏差 4.58%，但其吞吐比端到端高约 248 倍，不影响瓶颈排序。

## 4. 阶段时间

| 路径 | 样本 | URL mean/P95 | 等待响应头 mean/P95 | 读取正文 mean/P95 | 内容处理 mean/P95 | 回收 mean/P95 |
|---|---:|---:|---:|---:|---:|---:|
| 纯传输 | 4,883 | 0.57/1.30 µs | 2,136/4,562 µs | 1.96/3.46 µs | 0.19/0.28 µs | 1.52/2.29 µs |
| 端到端 | 4,883 | 1.16/2.46 µs | 2,175/4,491 µs | 3.67/9.90 µs | 164.07/237.29 µs | 6.45/16.00 µs |

端到端采样阶段合计 2,350.22 µs。依据 Little 定律，1536 个槽除以 659,908 pages/s 得到的平均槽周期为 2,327.60 µs；两者只差约 0.97%，因此阶段采样解释了超过 99% 的端到端墙钟路径，超过 95% 验收门槛。

响应头等待占单槽墙钟时间绝大多数，但这是可并行等待时间，不能直接解释为 Runner CPU。正文读取本身只有数微秒，瓶颈不在复制一个约 1.4 KiB 的正文。

## 5. Runner CPU 预算

使用三次中位数换算每页 Runner CPU：

| 成本中心 | 估算 CPU/页 | 占端到端 CPU |
|---|---:|---:|
| HTTP/请求执行栈 | 60.37 µs | 30.8% |
| 完整内容处理 | 96.10 µs | 49.0% |
| 调度、URL、缓冲、分配/释放和整合残差 | 39.62 µs | 20.2% |
| 端到端合计 | 196.08 µs | 100% |

这是独立路径中位数的工程分解，不等同于逐函数 CPU profiler；它用于决定重构顺序。完整内容处理虽然消耗约一半 Runner CPU，但单独能达到 193.4 万 pages/s，并可使用约 186 个核。它的容量是当前端到端的 2.91 倍，因此不是第一吞吐上限。

相反，纯传输只有约 71.6 万 req/s，端到端已经达到其 92.7%。当前吞吐首先撞上请求执行/网络数据面，然后才会撞上内容处理。

## 6. NUMA 共置对照

| 放置 | 纯传输中位数 | 端到端中位数 | 端到端 Runner 核心用量 | 三次最大偏差 | 失败 |
|---|---:|---:|---:|---:|---:|
| 源站独立 NUMA | 862,670 req/s | **671,662 pages/s** | **136.27 / 144** | 1.73% | 0 |
| 源站与 Runner 共置 | **1,012,167 req/s** | 602,743 pages/s | 114.30 / 144 | 1.86% | 0 |

共置让纯传输提高 17.3%，说明 Socket/回环局部性更好；但端到端反而下降 10.3%。隔离后端到端提高 11.4%，Runner 获得的实际 CPU 容量提高 19.2%。

这证明当前下降不是“Socket 不够快”，而是源站抢占同一 NUMA 域后，全局 Tokio 的 I/O 唤醒、同步内容处理、缓存和内存分配没有稳定的域所有权。192 vCPU 共置结果不能被解释为 192 vCPU PageSift 的纯扩展能力。

## 7. 前三成本中心与结论

### 第一：请求执行/网络数据面

纯传输上限约 71.6 万 req/s，最接近端到端上限。当前正式 Runner 使用全局 Tokio、逐页 Spawn 和 reqwest/hyper；这是第二步必须替换的第一对象。

### 第二：内容处理 CPU

完整内容处理约占端到端 CPU 的 49%，但具有 193.4 万 pages/s 的独立容量和接近全核的扩展能力。它不是第一堵墙，但在新执行器突破约 100 万后会成为下一瓶颈。

### 第三：调度、分配与生命周期整合

约 39.62 µs/页、占端到端 CPU 20.2% 的残差来自逐页任务、URL、Future、响应缓冲、DOM/Markdown 生命周期和跨线程释放。该部分应由固定 Slot、NUMA 本地 Arena 和所有权不迁移来消除。

## 8. Step 1 判定

本机组件归因验收通过：

- 三条核心路径三次离散度均不超过 3%。
- 阶段采样解释超过 99% 的平均槽周期。
- 前三成本中心已经明确。
- 所有正式探针 `failed = 0`，Runner `process_cpu_time_s` 有效。

尚未完成的外部复核：使用第二台主机运行源站，排除本机 loopback 和源站进程的全部干扰。该复核不会阻止第二步开始，因为固定 144 vCPU 的 NUMA 对照已经证明全局执行器/所有权模型存在问题；远端结果仍必须在 P2 最终验收前补齐。

## 9. 对第二步的约束

第二步只替换执行器，不同时重写 HTTP 协议和内容算法：

1. 保持相同 reqwest/hyper 传输和相同五类页面。
2. 移除逐页 `tokio::spawn`，改为固定 Slot 状态机。
3. 每个 NUMA 域固定 Worker、连接和内存所有权，禁止跨域工作窃取。
4. 用本报告的纯传输、端到端和 CPU/页作为唯一 A/B 基线。
5. 若相同传输下吞吐没有明确提高，则不进入第三步。
