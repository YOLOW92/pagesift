# PageSift 0.70 P2：10,000 域名真实互联网 HTTPS 基线

> 日期：2026-10-25（VPS UTC 记录为 2026-10-24）  
> 环境：Google Cloud `c4-highcpu-192`，Intel Xeon Platinum 8581C，192 vCPU / 96 物理核 / 2 Socket / 4 NUMA  
> 结论边界：本测试验证生产 `Scraper -> policy -> pagesift-net -> Rustls -> content` 公网路径，不代表新的 Mio Reactor 已完成 Rustls 适配。

## 测试设计

- 数据：`bench/data/top-1m.csv` 的前 10,000 个不同域名，目标集合 SHA-256 为 `f5e68e119f4693e07a2076244846469fc0568491e734b10c3ec300b0b283eed3`；
- 每个域名只提交 `https://<domain>/` 一次，不对单一公网站点重复施压；
- 强制 `engine=http`，关闭浏览器回退与结果缓存；
- 使用生产默认 robots、SSRF、重定向、证书验证和诚实 UA；
- connect timeout `3.5s`，total timeout `8s`；
- 拓扑自动给出初始全局并发 `1,536`，进程 FD 上限实测 `524,288`；
- CPU 只取 Runner 自身 `/proc/self/stat` 的 `utime + stime`。

这里的 `adaptive` 表示根据硬件/NUMA 自动生成初始配置。单页 `scrape` 入口目前没有接入 crawl 的运行时反馈门，因此本轮不能证明并发控制器在公网负载中进行了在线收敛。

## 解读

1. **公网链路不是 CPU 饱和场景。** 平均仅使用 1.723 个 CPU 核，主耗时来自 DNS、TCP/TLS、robots 和远端响应长尾；不能拿 `503.86 tasks/s` 与回环 90 万 pages/s 直接比较。
2. **10 秒时已完成 9,952 条，最后 48 条又消耗约 9.85 秒。** 尾延迟把最终任务速率从瞬时约 `995/s` 拉低到 `503.86/s`，说明固定 8 秒超时会形成明显的末尾屏障。
3. **失败不是单一调度故障。** DNS、访问屏障和网络/TLS 三类合计 3,381 条，占全部目标 33.81%；robots/SSRF 408 条属于策略拒绝，不应算 Reactor 传输失败。
4. **当前结果建立了生产 Rustls 公网基线，但没有验证新 Reactor。** 下一步应让新 Reactor 复用生产 DNS/SSRF/robots 入口，并以 Rustls `ClientConnection` 的非阻塞握手/读写状态接入 Mio，随后用同一冻结目标集做 A/B。
