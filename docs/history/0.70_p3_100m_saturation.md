## 控制器轨迹（attempt4）

- 容量：`1536 → 2272 → 5548 → 8669 → 1817 → 2272 Locked`。约 21% 进度锁定，之后保持稳定。
- 流水线：`48 Reactor + 144 内容线程` 起步；控制器依次探索 `64/128 inline 12%`、`80/112 inline 23%`、`96/96 inline 34%`，最终锁定 `80/112 inline 23%`。
- 分发：锁定 `local batch 2 / 4 次空轮询后 stealing / steal batch 1`。
- 约 99M 任务后仍为 `0 timeouts / 0 retries / 0 content failures / 0 transport failures`。

## 首次失败与保留证据

2026-10-24 的首次冻结运行完成了全部 `100,000,000` 个任务，但其中 `14,720` 个被记为失败，最终有效任务 `99,985,280`；抽检 `9,998/10,000`。门禁按设计拒绝该轮。原始日志保留在 `benchmarks/scale/results/0.70_p3_100m_saturation.log`，SHA-256 未变。

该轮的失败不是均匀噪声，而是 8 次离散跳增：`+533、+736、+3,276、+3,121、+3,619、+533、+736、+2,166`。旧遥测把正文校验失败和最终传输失败合并到同一 `failed` 计数，因此当时无法诚实区分两类根因。抽检缺 2 条是失败集合的派生结果，不是第二个独立故障。

失败轮报告的控制器轨迹、P0 对照和证据缺口分析仍然有效，见本文历史版本与 `git` 记录；本轮不删除、不覆盖该证据。

## 失败后的通用修正

### 1. 失败分类与可观测性

Runner 报告新增 `content_failed` 与 `transport_failed`，并把正式完整性检查移到 JSON 落盘之后。即使门禁失败，也保留原生 CPU、NUMA、重试、超时、队列和控制器报告，再以非零状态退出。

### 2. 源站文件描述符上限

后续诊断出现 `1,837` 个传输失败。三组 A/B 定位到 `systemd-run --user` 启动的源站继承了 soft `NOFILE=1024`：连接扩容到 2,272/2,840 后源站 FD 耗尽，内核完成握手但源站无法 `accept`，客户端在 `Reading` 超时。正式门禁现在：

- 以 `LimitNOFILE=1048576` 启动源站；
- 启动后读取 `/proc/<pid>/limits`，soft NOFILE `< 65,536` 时拒绝开始；
- 把 `origin.soft_nofile` 写入 provenance meta。

### 3. 容量搜索：窗口证据与反向细搜

旧控制器用单样本 EWMA 和固定 `1.005` 阈值，导致震荡和锁定在错误点。现在：

- 容量、流水线和分发统一使用 `SampleWindow` 窗口均值和相对 SEM；
- 显著性阈值 = `max(floor, noise_sigmas × 两窗口相对 SEM 合成)`，不再用固定百分比硬拒真实提升；
- 大步长回归时立即反向并以 `step = 1` 做局部细搜，而不是继续在同一方向折半；
- 一侧穷尽后先以 `step = 1` 试另一侧，再允许锁定；
- 控制器按 `Locked` 轮流运行，避免多控制器同时换参。

容量探针保持 `settle=1 / min=3 / max=5 / SEM=1%`。更短的 `settle=0 / min=2 / max=4` 实测更差（持续 957,978 pages/s，尾部 975–982k），已回退。

### 4. 源站线程超订（本轮吞吐上限的真正原因）

源站此前按 `runtime_worker_cpus()` 为每个逻辑 CPU 创建一个 tokio worker，在本机是 192 个线程；Runner 同时有 48 Reactor + 144 内容线程，也是 192 个绑核线程。两者在 192 个逻辑核上形成 2:1 超订，抬高了 loopback 往返延迟，使 Runner 在约 929 连接、约 100 万 QPS 附近提前饱和。

源站是夹具，不是受测系统。现在默认线程数为 `physical_cores / 4`，夹在 `8..=32`（本机为 24），仍由拓扑推导，不针对 192 vCPU 写死。A/B（同一 Runner、同一 100M、`--connections 0`）：

| 源站线程 | 持续 QPS | 稳态 | 最终连接 | 失败 |
|---:|---:|---:|---:|---:|
| 16 | 903,273 | 901,018 | 5,548 | 0 |
| 24（默认） | 1,063,422 | 1,060,451 | 8,669 | 0 |
| 24（复现） | 1,096,289 | 1,117,151 | 2,272 | 0 |
| 24（复现） | 1,100,667 | 1,113,129 | 2,272 | 0 |
| 32 | 1,061,842 | 1,064,197 | 6,935 | 0 |
| 48 | 1,038,572 | 1,052,564 | 1,817 | 0 |
| 192（旧默认） | 954,747–981,172 | 970,660–997,285 | 929/1,162 | 0 |

16 线程时源站自身成为瓶颈；24–32 线程最佳；48 线程略降；192 线程超订最差。该结论只改变夹具的线程预算，不改变 Runner 的容量、流水线或分发算法。

### 5. 分配器与内容路径

Runner 使用 `mimalloc` 作为全局分配器，降低多线程分配竞争。内容路径保留 `TitleSignature` 每页一次、ASCII 标题快速路径、空白计数/折叠快速路径；这些改动在 20M 固定对照中，噪声自适应显著性先把吞吐从 `967,185` 提升到 `986,302 pages/s`，再加入 `mimalloc` 后达到 `989,854 pages/s`。该固定对照只用于隔离核心吞吐，不作为自适应路径的配置建议。

## 与 P0 的诚实比较

P0 正式基线为 `427,033.53 pages/s`、Runner CPU 约 `43.8%`、峰值 RSS `627.5 MB`。本轮 `1,092,854.41 pages/s` 是同口径 Runner 持续吞吐，约为 P0 的 `2.56×`；Runner 平均使用 `133.13 / 192` 个逻辑核（`69.34%`），峰值 RSS `865.7 MiB`，仍低于 `2 GiB`。机器尚未被 Runner 跑满，吞吐上限受 loopback 往返延迟和夹具/受测进程的 CPU 共存方式约束，而不是 CPU 算力耗尽。
