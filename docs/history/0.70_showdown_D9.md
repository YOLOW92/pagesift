# 0.70 十域对决 · D9 动态渲染（CDP）

## 口径

| 项 | 值 |
| :--- | :--- |
| 测试床 | 自建确定性 SPA 源站（`benchmarks/crawl/scripts/d9_origin.py`），7 个场景各带唯一标记 |
| 判定 | 输出里是否出现该页的唯一 `MARKER-*` |
| 引擎 | PageSift `--engine http`（纯 HTTP）与 `--engine browser`（CDP + Chrome）；对照 Playwright |
| 浏览器 | Chromium 131（Playwright 官方镜像内），PageSift **以非 root 运行、沙箱开启** |
| 内存 | 每个参赛者 10 GiB 上限 |

## 七个场景

| 页面 | 动态内容形态 |
| :--- | :--- |
| `static` | 纯静态（对照组） |
| `csr` | 正文完全由 JS 注入 `#app` |
| `delay` | `setTimeout` 1500ms 后才注入 |
| `scroll` | 滚动事件触发懒加载（页面自己 800ms 后派发 scroll） |
| `click` | 点击按钮才出现内容 |
| `canvas` | 文本画在 canvas 像素里，DOM 无文本 |
| `hydration` | 服务端给占位文本，JS 补水后替换 |

## 结果

| 页面 | PageSift http | **PageSift browser** | Playwright |
| :--- | :---: | :---: | :---: |
| static | ✅ | ✅ | ✅ |
| csr | ❌ | ✅ | ✅ |
| delay（1500ms） | ❌ | ❌ | ✅ |
| scroll | ❌ | ❌ | ✅ |
| click | ❌ | ❌ | ❌ |
| canvas | ❌ | ❌ | ❌ |
| hydration | ❌ | ✅ | ✅ |
| **合计** | **1 / 7** | **3 / 7** | **5 / 7** |

## 时延

| 引擎 | 单页耗时 |
| :--- | ---: |
| PageSift http | 0.18–0.30 s |
| PageSift browser | 0.46–0.50 s |
| Playwright（含固定 2s 额外等待） | 约 2.55 s |

PageSift browser 引擎比 Playwright 快约 **5 倍**，因为它不等固定时长，而是以网络空闲等信息判断渲染完成。

## 分析：我们输在哪

| 场景 | 为什么没命中 |
| :--- | :--- |
| **delay（1500ms）** | PageSift 在页面网络空闲后即判定渲染完成，不等 `setTimeout` 的延迟注入。Playwright 侧因为脚本里固定多等了 2 秒才命中。 |
| **scroll** | 需要主动滚动触发。PageSift 当前不做滚动，Playwright 也没做——但页面自身在 800ms 后派发 scroll 事件，Playwright 多等的 2 秒覆盖到了，PageSift 没等到。 |
| **click** | 需要人机交互。**两者都失败**，这是合理的——渲染引擎不应自己点按钮。 |
| **canvas** | 文本在像素里，DOM 无文本。**两者都失败**，这是能力边界（需要 OCR）。 |

**核心差距是「等待策略」**：Playwright 用的是固定 2 秒兜底等待，PageSift 用的是网络空闲判定。
后者快 5 倍，但对 `setTimeout` 这类延迟注入不够耐心。

这**不是渲染能力缺失**——`csr` 和 `hydration` 两个真正的 SPA 场景我们都正确渲染了。
差距在「渲染完成后该再等多久」这个参数上。

## 结论与建议

1. **PageSift 的 browser 引擎确实能渲染 SPA**：`csr`（纯客户端渲染）与 `hydration`（补水替换）都正确命中。
2. **`delay` 类场景可以通过增加一个"渲染后静默等待"参数解决**，代价是每页多花时间。
   当前 0.46s vs Playwright 的 2.55s 已经省下大量时间，加 300–500ms 静默期仍显著更快。
3. **`click` 与 `canvas` 两者都失败**，属合理边界：前者需要交互，后者需要 OCR。
4. 与 0.50 的比较无法进行——0.50 报告的 D9 用的是另一套测试床（158.4 ms/render、100% canvas pass），
   本次口径完全不同，不作对照。

## 环境备注

本机 Chrome 沙箱需要 `--security-opt seccomp=unconfined --cap-add=SYS_ADMIN` 且以非 root 运行，
因为 Ubuntu 23.10+ 默认限制非特权 user namespace。
PageSift 在 root 下**主动拒绝**启动浏览器（坚持不关闭沙箱），这是正确的安全行为，本次予以保留。
