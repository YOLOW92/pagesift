# 混合增强基准（Mix）：规则（草案，2026-10-27）

目的：在公开基准之外，用一套按规则随机抽样、混合真实场景、谁都能复现的测试集，比较 pagesift 与同类工具在
**质量、速度、资源、稳定性**上的表现。题目是我们出的，所以下面每条规则都是为了让结果经得起别人检查。

状态：草案。规则定稿后才开始抽样；抽样之后规则、样本、评分都不再改。要改，就另起一个新版本号，旧版本的结果照样保留。

---

## 一、六条硬规则

1. **先定规则，再抽样。** 类别、配额、抽样方法、评分方式、每个工具的运行参数、预期结果，都先写进本文件并提交
   （提交号就是这一版的“冻结点”），然后才抽样、才跑。
2. **抽样不挑。** 只按公开列表和固定随机种子抽（见第三节），抽到什么用什么；抓取失败的样本照实记成“不可用”，
   不换。只排除违反 robots.txt 的样本，以及需要登录、付费的页面。
3. **弱项照样放。** PDF 表格、阅读顺序、pptx 这些我们目前不领先的类别，配额和别的类别一样，分数如实发布。
4. **不靠人工标注，标准答案也不来自任何参评工具的输出。** 质量分只用现成的公开标注集，或从原始文件本身
   （文本层、XML）由不参评的独立库读出的答案；没有标注的随机样本只评能自动判断的项目（见第二节）。每条答案都记录来源。
5. **对所有工具一视同仁。** 同一份输入、同一个评分脚本、同一台机器、同一组资源上限；每个工具都用默认参数，
   另外允许一组“官方推荐配置”，并写明是哪一组。
6. **全部公开。** 抽样脚本、样本清单（URL 与 SHA-256）、能再分发的文件本身、每个工具的原始输出、评分脚本、
   机器配置、工具版本锁定文件都进仓库。别人用一条命令就能重跑。

### C. 压力与稳定性

| 子类 | 内容 | 评什么 |
|---|---|---|
| C1 模糊测试样本 | pagesift-fuzz 找到过的全部卡死、爆内存样本（已公开在仓库） | 每个工具：崩溃数、超时数（单份 60 s）、超内存数（单进程 4 GB） |
| C2 并发 | 同一批 A2 页面，1、4、16 并发 | 吞吐、p50 和 p95 延迟、峰值内存 |
| C3 长时间运行 | 服务形态的工具连续处理 A2 全集 3 遍 | 内存是否持续增长、错误率是否上升 |

**规模目标**：全部工具跑完控制在约一小时（16 核、15 GB）。用模型的工具（marker、docling）只跑每个子类按固定种子抽的 10%。

## 三、抽样与复现

- **随机种子**：每个子类一个固定种子，写在 `bench/mix/seeds.toml`；种子在本文件冻结时一并提交，之后不改。
- **网页快照**：抽样时抓一次，存成 WARC，记录抓取时间、最终 URL、HTTP 状态、SHA-256。所有工具读同一份快照，
  不各自联网，排除网站变化和反爬的影响。抓取遵守 robots.txt，UA 写仓库地址。
- **能再分发的直接放进仓库或发布附件**：olmOCR、公开标注集、arXiv（看许可）、政府公开文件、古登堡、维基共享资源。
  **不能再分发的只放 URL、抓取时间和 SHA-256**，附抓取脚本；别人重抓后用哈希核对是不是同一份，对不上的样本单独列出。
- **工具版本锁定**：Python 工具用带哈希的 requirements 锁文件，Node 工具用 lockfile，Rust 工具记提交号，
  pagesift 用发布的二进制。全部列在 `bench/mix/tools.lock.md`。
- **机器与资源**：写明 CPU、内存、系统；每个工具单独一个进程，同样的 CPU 和内存上限（systemd-run）；
  测速走 bench.lock，不和别的任务并行。
- **一条命令重跑**：`bench/mix/run.sh`（抽样 → 快照 → 各工具运行 → 评分 → 出表）。每一步都可以单独重跑。

## 四、参评工具（2026-10-27 用户拍板）

每个领域三个：**一个 Rust 项目 + 两个业界公认、别人做对比也常拿来比的项目**。现有各领域的对比表（docs/benchmarks.md）
是另一份数据，保留不动。极限测试（本基准的 A4、B3、C 部分）用同一组工具。全部默认参数，安装命令写进 tools.lock.md，
不做 Docker 镜像，不比收费 API。

| 领域 | Rust | 业界公认 1 | 业界公认 2 |
|---|---|---|---|
| 网页正文提取 | crw（crw-extract） | trafilatura | Mozilla Readability（+ Turndown） |
| 抓取 | spider（spider-rs） | Scrapy | Crawl4AI |
| PDF | pdf_oxide | pymupdf4llm | Docling（用模型，只跑 10% 抽样，报 GPU 和 CPU 耗时） |
| Office 与电子书 | extractous | MarkItDown | Docling |

某个 Rust 项目装不上或不支持该领域输入时，换同领域下一个 Rust 候选（PDF：pdf-extract；Office：docx-rs 系列不算，
需要能整份转文本的），并在 tools.lock.md 写明原因。

## 四之二、时间上限

题目越复杂越好，但每题有时间上限，到点没出结果就算“没完成”：

- **上限怎么定**：每个子类先在公开基准上测出各工具单份耗时的中位数，取其中最慢工具的 10 倍作为该子类的单份上限，
  再设一个整批总上限（单份上限 × 份数 × 0.5）。上限在冻结前写进 `bench/mix/limits.toml`，之后不改。
- **没完成怎么算**：超时、崩溃、超内存、空输出都算没完成；整批到点后，没跑到的也算没完成。
- **分数报三样**：
  1. 完成率（越高越好）；
  2. 全部题目的分数，没完成的按零分（越高越好）；
  3. 只算所有工具都完成了的题的分数（越高越好），排除速度因素，单比质量。
- 第 2 项体现“做得完”的优势，第 3 项防止别人说我们靠速度赢分；两项都发布。

## 五、发布方式

- 和公开基准分两张表，这张注明“自建，规则和数据见 bench/mix”。
- 每个数字标明越高越好还是越低越好，并能追溯到结果文件。
- 每个类别都报：质量、速度、峰值内存、失败率（崩溃、超时、超内存、空输出）。
- 我们输的类别照样写进 README 和发布说明，不藏在附录里。
- 预期先写在本文件第六节；结果和预期不一致的地方，在结果文件里逐条说明。
